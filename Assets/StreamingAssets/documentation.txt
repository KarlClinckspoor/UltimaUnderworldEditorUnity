ULTIMATE UNDERWORLD EDITOR - DOCUMENTATION
==========================================

Editor for Ultima Underworld I (The Stygian Abyss, "UW1") and Ultima Underworld II (Labyrinth
of Worlds, "UW2"). Originally written by krokots (2019); extended for UW2, saved games, mods and
safer saving since 0.4. This file is opened by Help > Documentation.

Where this documentation says "the game's source", it means the commented reconstruction of
both games' code in underworld-exhumed (https://github.com/abedegno/underworld-exhumed). File
and function names in brackets, like [event/TRIGGER.C UseTrap], point into it, so you can check
any statement yourself. "UW1 only" and "UW2 only" mark the differences between the games.

1) GETTING STARTED
------------------

1.1) Opening a game
  File > Open game... asks for the game's executable (UW.EXE or UW2.EXE), then for the folder
  to edit: the game's DATA folder (the levels a new game starts with) or a saved game folder
  (SAVE1..SAVE4: the levels as that save left them, plus the player and the conversation
  variables). The editor detects which game it is. If something is already open, it offers to
  save first.

  Back up the game folder before editing. The editor also keeps its own backups (see 5).

1.2) What is stored where
  DATA\LEV.ARK      the levels (tiles, objects, the automap, map notes; UW2 also timers)
  DATA\STRINGS.PAK  every text: object names, books, scrolls, writings, text traps, conversations
  DATA\CNV.ARK      the conversations (compiled code)
  DATA\OBJECTS.DAT, COMOBJ.DAT, TERRAIN.DAT, SKILLS.DAT, CMB.DAT, SHADES.DAT  game tables
  DATA\*.TR, *.GR   textures and pictures
  SAVEn\LEV.ARK     the levels of that save; SAVEn\PLAYER.DAT the character; SAVEn\BGLOBALS.DAT
                    the conversation variables; UW2 also SAVEn\SCD.ARK (schedules)
  UW.EXE / UW2.EXE  where a new game starts (Tools > New game start square)

  A new game copies DATA's levels into the save when the player first enters each level, so an
  edit to DATA shows in a NEW game (or in levels a save has not visited yet). To change a game
  in progress, open its save folder.


2) MAIN EDITOR VIEW
-------------------

2.1) Controls
  W/S/A/D move the camera, Q/E zoom. The mouse buttons depend on the mode (below).
  Right mouse button over a tile or object opens a context menu in object mode.

2.2) Modes panel
  Bottom left: the editor mode and the level. UW2 levels are chosen by world (Britannia, the
  Prison Tower, Killorn Keep, the Ice Caverns, Talorus, the Scintillus Academy, the Tomb of
  Praecor Loth, the Pits of Carnage, the Ethereal Void) and a slider for the level inside it.
  A UW2 world has room for 8 levels; an empty slot can be made into a level.

2.3) Object mode
  Left click selects an object and shows its properties (top right). Drag an object to move it:
  the drag starts after the mouse has moved 5 pixels, so a click never moves anything. A faint
  copy of the object shows where it will land. Dropping it on a container, a critter, a door,
  a wand or a lever puts it inside (a sack holds items, a critter carries them, a door takes
  locks and door traps, a wand takes a spell, a lever takes triggers). Traps and triggers
  lying on the floor are not drop targets: add objects to them from their properties panel.
  Dropping off the map puts the object back.
  Moving a trap or trigger keeps its height, which is data for many of them (a teleport's
  level, a variable's number). It lands where you drop it, except the traps whose fine position
  is data too: they keep it and only change square (the shadow shows them at their kept spot).
  These are the change terrain, set variable and check variable traps, and in UW2 also the
  teleport, hack, inventory, change from, oscillator, proximity and pit traps and the pressure
  plates. A trigger's target square (quality, owner) does not follow it: change it in its panel.
  The properties panel also lists what links to the object ("Linked from"), the triggers whose
  chain runs on its square, and the squares it acts on (a trigger's target, a teleport's
  destination, where a trap's chain runs); each has a button that goes there. Those squares
  are marked on the map with red crosshairs while the object is selected.
  Right click an object: "Copy", "Remove", "Add trigger", "Inventory" (select an object inside
  it), and "Link trigger", "Link trap" or "Link lever" depending on the object. Right click a
  tile: "Add object", "Add move trigger", "Add trap", "Paste object".

2.4) Tile mode
  Left click selects a tile and shows its properties. Holding the right button paints tiles with
  the template shown above the modes panel. The mouse wheel over the selected tile changes its
  height; objects lying on the floor move with it, doors are repositioned.

2.5) Texture mode
  Paints the floor and/or wall texture chosen above the modes panel (toggles choose which).

2.6) Player start
  With DATA open, the smiling face is where a new game puts the player on level 1. It is not in
  the level data but in the executable; Tools > New game start square changes it. With a save
  open, it is where the save's PLAYER.DAT puts the player, on that level (the editor opens on
  it); Tools > Character in a save changes it. The game checks none of this when it restores a
  save: without PLAYER.DAT the restore fails, and a level or square that is wrong (off the map,
  solid rock) is used as it is. The editor says so after loading and then shows no face.
  Both windows' "Use the selected tile" take the tile selected in tile mode (green outline) or
  the square of the object selected in object mode, not the tile under the mouse.

2.7) When the editor is not in front
  While another window has the focus the editor ignores the mouse and keyboard (it no longer
  selects objects under another window) and draws only 5 frames a second. Autosave still runs.


3) TOP MENU BAR
---------------

3.1) File
  Open game...   choose the executable, then DATA or a saved game (see 1.1).
  Load           load the last opened game again.
  Save           write the edits to the game's files (see 5).
  Exit

3.2) Levels
  Clear Levels   erases all map data and, optionally, the conversations. UW1 is left with 9 empty
                 levels (level 1 keeps an open square at the start position).
  Key Editor     the key descriptions. A key's number is its owner field; a lock opened by it
                 has the same number. Buttons find a key or lock with a number (and the next or
                 previous one). UW1 and UW2 have 63 key numbers (1-63).
  Mantra Editor  the shrine mantras (UW1).

3.3) Objects
  Level Objects  the objects of the current level; clicking one centres the camera on it.
                 Green: active critters (on the map, not templates inside create object traps).
                 Yellow: animated objects. The number of an object is its "address" (index):
                 0-255 are mobile objects (critters, missiles; 27 bytes), 256-1023 static ones
                 (8 bytes). Object 1 is the player in a save.
  Add Object     spawns an object at the camera's centre (or right click a tile).
  Object Editor  the object tables (OBJECTS.DAT, COMOBJ.DAT):
                 In game description - the name; "_" marks where the name starts after an article,
                   "&" separates the plural.
                 Pickup flag - can be picked up.
                 Is talisman - COMOBJ "fate" 10. In UW1 these are the eight talismans: one thrown
                   into the lava pit of level 8 (after Garamon is laid to rest) is destroyed and
                   counted (see 12), and Lore 3 describes them specially.
                 Quality enabled - shows a quality ("Quality description") and can wear out.
                 Height - used for critters and 3D models.
                 Weapon: slash/bash/stab damage, minimum and maximum swing charge, swing speed,
                   skill (3 sword, 4 axe, 5 mace, 6 unarmed), durability (255 unbreakable).
                 Missile, ranged weapon (ammunition: 0 sling stone, 1 bolt, 2 arrow), armour,
                 critter (attack, experience, equipment damage, sprite and palette, three
                 attacks, inventory), container properties.
  Floor Editor / Wall Editor  TERRAIN.DAT: what each texture is (water, lava, ice...) and its
                 look description. UW1 has a type per wall and per floor texture; UW2 one table of
                 256 for T64.TR.

3.4) Graphics
  Level Floors / Walls / Doors  which textures the current level uses. UW1: up to 10 floors, 48
                 walls, 6 doors (plus the secret door and portcullis; the last ordinary door is
                 massive, unbreakable). UW2 levels pick from one shared list of 256 textures.
  Floors, Walls, Doors   the textures themselves: replace them with PNGs (floors 32x32, walls
                 64x64, doors 32x64). UW1 can also add textures (to 256). Colours are matched to
                 the game's palette.
  Switches / Levers, Other   levers, switches, writings, graves, bridges, pillars and so on; the
                 replacement must keep the original size.
  Generic Portraits / NPC Portraits   conversation portraits (UW2: 64x70).
  Object Graphics   object sprites (most 16x16), each with one of the game's 16-colour palettes.
  Export To PNG     writes the game's pictures to the Export folder.
  Only the pictures you replaced are written; a picture that can't be written is listed after
  saving.

3.5) Strings
  String list    every string block of STRINGS.PAK. Books, scrolls, writings, graves and text
                 traps get and free their texts automatically when you create, copy or delete
                 them. Conversation strings are written when a conversation is compiled.

3.6) NPC's
  Play conversation   runs a conversation as the game would. When it calls a built-in that needs
                 the game (an inventory, a quest flag, UW2's clocks and teleports), a window asks
                 for the value the game would return. Debug mode and single steps help find
                 faults; Clean conversation resets its saved variables; Parameters set the
                 starting values (attitude, time...).
  Add / Edit / Delete conversation   see 6. A new conversation in a slot no saved game has seen
                 starts with all its variables at 0 in existing saves.

3.7) Help
  Documentation  this file.


4) TOOLS MENU
-------------

  Object fields (selected object)   every bit of the selected object's record, with what the
       game's source says it means and how sure that is. Fields that are list structure (item
       id, next, a container's link) are shown but locked.
  Find items in all levels   search every level by item, owner, quality, enchantment...
  Fixes   consistency checks of the level lists (the free lists, objects reached twice or not
       at all, the active critter list, trap trigger counts) with automatic fixes, and an item
       cleaner that removes loose items by category (quest items and Garamon's bones are kept).
  Triggers and traps of this level   every trigger with where it lies, the square its chain
       runs on and the chain itself, then the traps no trigger reaches (door traps, and those a
       schedule, a conversation, a hack or the game's code fires, or nothing). Each entry
       selects its object.
  Class skills and attributes (SKILLS.DAT), Item combinations (CMB.DAT), Light levels
       (SHADES.DAT)
  Saved games   list and rename the save slots, edit each conversation's saved variables
       (BGLOBALS.DAT) by name.
  Character in a save   PLAYER.DAT: name, attributes, skills, vitality, mana, level, experience,
       and the position (level, square, heading).
  Quest flags and variables in a save   PLAYER.DAT's game state (10.1): UW1's quest flags
       0-31, quests 32-35 and the 64 game variables; UW2's quest flags 0-127, quests 128-143,
       the 256 numbered variables and the 16 X clocks. Known meanings are named. "Only
       non-zero" hides the rest.
  New game start square   writes the start square into the executable.
  Built-in 3D models   view the models drawn from the executable (door frames, pillars, levers,
       benches...) and export them as OBJ.
  Export as mod   packs your changes (compared with the .BKP backups or an original game folder)
       into a .uwmod package for the mod manager. A saved game can be exported alone.
  Autosave and backups   the autosave interval (0 = off) and how many backup versions to keep.
  Schedules (UW2 SCD.ARK)   the schedules that move NPCs and the plot by the clocks (see 10.5).
  Automap and map notes   which squares the player has mapped, and the notes written on the map.
  Level light (UW2)   DL.DAT's minimum light for the shown level, and the light flag of its
       squares: shows the flagged squares, toggles the selected tile, or sets or clears the
       flag on each tile clicked in tile mode (see 10.7).
  Show the randomizer tools   Sector mode and the zone tools (work in progress).
  Log conversation steps   writes every step of converting and playing conversations to the
       Unity log (slow; for debugging).


5) SAVING, BACKUPS, AUTOSAVE AND UNDO
-------------------------------------

5.1) Saving
  File > Save writes only the files whose bytes changed, each first to a temporary file that then
  replaces the original, so a crash can't leave half a file. Unchanged files keep their dates.

5.2) Backups
  The first time the editor changes a file it keeps the original beside it as NAME.BKP. Each
  later change also keeps the previous version in "Editor backups\<folder>\<name>.<date-time>"
  next to the game; 10 versions are kept by default (Tools > Autosave and backups, up to 1000).
  In a saved game the .BKP follows the game: if the game saved over the file since, the .BKP is
  refreshed. Export as mod compares against the .BKP files.

5.3) Autosave
  Every 10 minutes by default (0 turns it off), only if you edited something, and only while no
  dialog is open and you are not typing or dragging. An autosave does NOT write your game: it
  copies DATA, CRIT, the executable and the open save into "Editor autosaves\<date time>" next to
  the game and saves your edits there. As many autosave folders are kept as backup versions.
  To use one, copy its files back over the game's.

5.4) Undo
  The Undo button takes back moving, deleting, putting objects into containers and taking them
  out (30 steps). It restores exactly what the action changed and keeps any later edits (for
  example, a tile you changed after deleting an object). The level is rebuilt afterwards, so the
  selection is cleared. Field edits in the properties panel and tile painting are not undoable.


6) CONVERSATION EDITOR
------------------------
  This is a resizable and movable window.
  6.1) Main view
      In here you add new conversation nodes, and connect them. This is controlled by dragging LMB
      or using W/S/A/D keys.
      Use RMB on it to add a new conversation node.

  6.2) Right panel
      NPC Name - used to name an NPC. This will save only after successful compiling.
      Saved variables count - the number of conversation variables saved after the conversation
        ends (in BGLOBALS.DAT of a save). Changing it for a conversation that existing saves have
        already used breaks those saves' variables for it; a new conversation is safe.
      Saved variables - used for naming these variables.
      Barter strings - used for changing default barter dialogue.
      Liked & Disliked items - used for adding items or categories of items that NPC will favour /
      ignore in barter.
      Find start - used to quickly find starting node.
      Find node - used to find any node by it's name.
      Save - saves the conversation's editor file (DATA\conversation_N.dat, next to CNV.ARK) so you
      can
        edit it again later. This does not change the game.
      Compile - converts the conversation into the game's code. It checks the game's limits first
        (code size, 512 strings, the answers a menu can show); if anything fails, the conversation,
        its strings and the NPC name stay exactly as they were. A compiled conversation is written
        to
        CNV.ARK and STRINGS.PAK on File > Save.

  6.3) Conversation nodes
      This is where you program your conversation. You can move them around and link them by
      clicking on "output"
      (orange) circles or "input" (blue) circles.
      Right clicking on a node (not the input field, but the border / main panel) will create
      context menu.
      Node name can be changed by clicking on it.

  6.4) Conversation node conditions
      Each node can have multiple "conditions" or "outputs" that can lead to different nodes. You
      can add them by
      clicking RMB over a node (not it's input field) and choosing "Add condition". This will add
      another smaller
      input field and a orange circle right of node. Clicking on this orange circle will create
      another context menu.
      Remove if statement - removes the input field (the condition will always be true).

  6.5) Conversation flow
      Conversation starts in a "staring" node (which you define by RMB clicking on a normal (green)
      node and choosing
      "set as conversation start". It then reads all code within it's main input field. Then, if
      there are conditions,
      it will start from the top condition and go through to bottom condition. First it checks if
      the condition is true
      (the input field is filled with any kind of condition, or erased completely). If it is, then
      the conversation jumps
      to the node that condition is leading. If no conditions are true, or there are no conditions
      on the current node,
      the conversation will end.

  6.6) Variable types
      There are couple of variable types used in conversation editor.
      - "Saved variables" - these variables are global and will be saved after conversation ends.
      Saved variables are defined only on "Saved variables" menu.
      - "Global variables" - these variables are global but are not saved after conversation ends.
      Global variables can only be defined in starting node. Example :

      global Pos

      This will create global variable called "pos".
      - "Local variables" - these variables are not global, and will only be valid within ONE node.
      Example :

      local att

      This will create local variable called "att".
      One special global variable is called "response" and thus this name can't be used. It is used
      to store player responses.

  6.7) Arrays
      You can define arrays by using word "array" after declaring the type of a variable. Then you
      add [n]
      where n is array length. Example:

      global array InvPos[4]
      local array invIds[4]

      After declaration you get particular array element by adding [n] where n is array element (0
      index based)
      Example:

      local pos = invPos[0]

  6.8) Operators
      Supported operations are :
      sum : +
      substraction : -
      multiplication : *
      division : /
      modulo : %
      Logical operations :
      or : |
      and : &
      not : !
      Comparison operations :
      ==, !=, >, <, >=, <=

  6.9) If and endif
      These are used to compare variables. "If" must be closed by an "endif". Example :

      local pos = 2
      local other
      if (pos == 2)
        other = 10
      endif
      if (other > pos)
        pos = pos + 1
      endif

  6.10) Functions

      void Say(string str)
        Most common function used for NPC to say something. Example :

        Say("Hello world!")

      void Responses(string resp_a, ..., resp_d)
        Stops conversation and creates a menu for player to choose one of up to four responses.
        Example :

        Responses("Hello to you too!", "Hey dude", "Who are you?", "Die monster!")

        It then stores the response in "response" variable. This is "1" based! So if player chooses
        "Hello
        to you too!" response will be 1. Example:

        Say("Hello world!")
        Responses("Hello to you too!", "Hey dude", "Who are you?", "Die monster!")
        if(response == 1)
          Say("Nice to see you!")
        endif
        if(response == 2)
          Say("Yo")
        endif
        if(response == 3)
          Say("Why I'm the great Murad of Bolothia, how you have never heard of me?")
        endif
        if(response == 4)
          Say("Wait, wha...")
        endif

      void ResponsesIf(condition cond_a, ..., cond_d)
        The same as "Responses" but uses "conditions" instead of plain strings. Condition is a
        string followed by
        variable (or not, if required). Example :

        Responses("Hello to you too!", "Hey dude" if pos, "Who are you?" if other, "Die monster!")

        It checks variables if are greater than 0. If true, that response will be printed, if not,
        it will not be printed.
        In this example, if pos and other is 0, there will be only two responses (first and fourth).

      void Jump(string nodeName)
        Instantly moves conversation to another node. Example :

        Say("Hello world!")
        Responses("Hello to you too!", "Hey dude", "Who are you?", "Die monster!")
        if(response == 1)
          Jump("Node 10")
        endif

      void End()
        Ends conversation. This is not required most of the time - conversation will end itself
        when reaching
        end of node and no conditions are met or present.

      void Description(string str)
        The same as "Say", but the string printed is in black font, in UW this is used to describe
        something
        going on around the conversation.

      int Ask()
        This will stop conversation and ask player for input. Used in UW's for asking for passwords
        and in Murgo
        conversation. Can be used to get integer values too, and then converted to integers by
        "ValueOf".
        This returns the pointer to the string that player had input. Example:

        Say("Stop right there, what's the password!")
        local pass = Ask()
        local comp = Compare("Kamehameha", pass)
        if(comp == 1)
          Jump("Node 2")
        endif

      int Compare(string str, int ptr)
        This will compare a string to a previously inputted (is this a word?) string. For usage see
        "Ask".
        Returns 1 if strings are identical, otherwise 0.

      int Contains(string str, int ptr)
        The same as "Compare", but checks if the string contains another, not if they are equal.

      int Random(int max)
        Generates random value from 1 to max. Example

        local rnd = Random(64)
        if(rnd > 40)
          Jump("Node 4")
        endif

      int ValueOf(int ptr)
        Converts string to an integer value. Used with "Ask". If string is not a integer, it will
        return 0.
        Example :

        local val = Ask()
        val = ValueOf(val)
        if(val == 2)
          Jump("Node 4")
        endif

      int GetAttitude()
        Returns current NPC attitude. 0 - hostile, 1 - upset, 2 - mellow, 3 - friendly. Example:
        local att = GetAttitude()
        if(att == 3)
          Jump("Node 10")
        endif

      int GetTalked()
        Returns 1 if already talked to that NPC.

      int GetHomeX()
      int GetHomeY()
        Returns the X/Y of NPC "Home" (the tile that NPC will always try to come back)

      int GetProperty(string propName)
        Returns current value of a NPC property, possible values :
        "game_mins":  minutes passed ?
        "game_days":   in game days passed?
        "game_time":   ?
        "riddlecounter":  ?
        "dungeon_level":  current dungeon level
        "npc_name":   pointer to NPC name string
        "npc_level":   NPC level (?)
        "npc_talkedto":  if already talked to NPc
        "npc_gtarg":   NPC target (1 - player)
        "npc_attitude":  NPC attitude
        "npc_goal":   NPC current behaviour (check objects to see what it means)
        "npc_power":   ?
        "npc_arms":   ?
        "npc_hp":    NPC current HP
        "npc_health":   ?
        "npc_hunger":   ?
        "npc_whoami":   NPC ID
        "npc_yhome":   NPC Home X
        "npc_xhome":   NPC Home Y
        "play_sex":   ?
        "play_drawn":   If player weapons is drawn?
        "play_poison":   ?
        "play_name":   pointer to player name string
        "new_player_exp":  gained XP ?
        "play_level":   player level?
        "play_mana":   player current mana
        "play_hp":    player current HP
        "play_power":   ?
        "play_arms":  ?
        "play_health":   ? something with poison?
        "play_hunger":   ?

      void SetProperty(string propName, int val)
        Sets the property to a value, check "GetProperty" to see possible values.

      int GetQuest(int questID)
      void SetQuest(int questID, int val)
        The quest flags, shared with the set variable trap's quest mode (see 10.1).
        UW1: quests 0-31 are flags (0 or 1), 32-35 are bytes (quest 32 is the Knight of the Crux,
        0-4). GetQuest above 35 returns how many talismans are left to destroy. The game's
        built-in shifts an int, so from conversations only quests 0-14 work reliably; setting 15
        also changes 16-31 [conv/BABLHACK.C set_quest].
        UW2: quests 0-127 are flags, 128-143 bytes. Set flags only to 0 or 1: other values spill
        into
        the neighbouring flags.

      int GetSex(string male, string female)
        Adds two strings to conversation string list and checks what sex is player character.
        Returns a pointer
        to the valid string. Example:

        local sex = GetSex("lad", "lass")
        Say("Hello $S:sex")

      int ArrayContains(array arr, int val)
        Checks if an array contains a value, returns the index of array element which contains this
        (1 based), or
        0 if did not find. Example :

        local array invPos[4]
        local index = ArrayContains(invPos, 1)
        if(index > 0)
          Jump("Node 3")
        endif

      int GetInventorySlots(array invIds, array invPos)
        Checks the "barter" area for items. Fills the provided arrays (must be 4 in size) with
        values found. The first
        (invIds) will be filled by object ID's found, the second (invPos) will be filled by objects
        master list
        positions found. It returns the number of objects found. Example :

        local array invPos[4]
        local array invIds[4]
        local slots = GetInventorySlots(invIds, invPos)
        if(slots == 0)   //No items found
          Say("No item found.")
          End()
        endif
        if(slots > 1)   //More than one item found
          Say("More than one item found")
          Jump("Multiple")
        endif
        local pos = invPos[0] //Getting the only item found in the barter area
        local id = invIds[0]

      int FindItemInBarter(int id)
        Searches the "barter" area for an item with specific ID. If found, it returns it's position
        in object
        master list. Example:

        local pos = FindItemInBarter(161) //Gold coins
        local count = CountItem(pos)  //Checking how many gold coins

      int FindItem(int id, int inventoryType)
        Searches specific inventory (not barter area) for an item with specific ID.
        If inventoryType = 0, it searches NPC inventory.
        If inventoryType = 1, it searches player inventory.
        Example:

        local pos = FindItem(186, 1)  //Bottle of ale

      int CountItem(int masterPosition)
        Returns item quantity of an item with master list position provided. Check
        "FindItemInBarter" for example use.

      int GiveMany(array itemPos, int itemCount)
        Transfers items to NPC inventory. Items master list position is stored in itemPos array.
        ItemCount is number of
        items to transfer (number of items in array to transfer). It returns 1 if transfered
        something, or 0 if
        transfered nothing. Example:

        local array invPos[4]
        local array invIds[4]
        local slots = GetInventorySlots(invIds, invPos)
        if(slots > 1)
          local result = GiveMany(invPos, slots)
          if(result == 1)
            Say("Thanks for these items!")
            Jump("Node2")
          endif
        endif

      int GiveItem(int itemPos, int quantity)
        Transfers a single item to NPC inventory. itemPos - item master list position. Quantity -
        seems to not work
        in UW anyway, -1 to ignore quantity - transfer whole item. But it always transfers all,
        so...
        Returns 1 if transfered item, or 0 if not. Example:

        local array invPos[4]
        local array invIds[4]
        local slots = GetInventorySlots(invIds, invPos)

7) OBJECTS
----------

7.1) The properties panel
  In object mode, left click an object (or pick it from Objects > Level Objects, or from the
  "Inventory" list of the object holding it) to show its properties in the top right corner.
  The panel has two tabs.

  Basic     what the editor understands about this kind of object, in plain terms: a door's
            lock and door traps, a trigger's target square and who can set it off, a trap's
            settings, a critter's attitude, goal, hit points and conversation, an item's
            quality, owner, enchantment or quantity. Buttons here add the objects that belong
            inside (a lock, a door trap, a template, the next trap of a chain) and link
            triggers to traps.
  Advanced  the raw fields of the object's record, described in 7.2: Type (the item id),
            Adress (the object's index, with the next and previous object of its list), Tile
            Pos (X / Y), Height, Enchanted, Invisible, Is quantity, Door, Direction, Flags,
            Quality, Owner and Quantity/Special. A mobile object (critter) also shows Home
            (X / Y), Attitude, Goal, HP and NPC ID.

  Use Basic whenever it offers what you need. The Advanced fields are written exactly as you
  type them, and two of them (Is quantity and Quantity/Special) decide how the game reads the
  object's link: a wrong value there can make the game treat an unrelated object as this
  one's contents, and break the level's lists. Tools > Object fields shows every bit of the
  selected object with what the game's source says it does; Tools > Fixes checks the lists and
  the trap trigger counts afterwards.

  Many of the descriptions below and in chapters 8 and 9 name fields that the Basic tab does
  not show for a given object (for example a trap's fine x or a timer's height). Set those in
  the Advanced tab: fine x and fine y are "Tile Pos (X / Y)", z is "Height", the heading is
  "Direction".

7.2) The object record
  Every object is a record of four 16-bit words. Critters and missiles ("mobile objects",
  indexes 0-255) have 19 more bytes for their AI (7.5); all other objects ("static objects",
  256-1023) have only the four words. The words hold these fields:

    Field          Bits             Advanced tab        Range
    item id        id word 0-8      Type                0x000-0x1FF
    flags          id word 9-11     Flags               0-7
    enchanted      id word 12       Enchanted           0/1
    door           id word 13       Door                0/1
    invisible      id word 14       Invisible           0/1
    is quantity    id word 15       Is quantity         0/1
    z (height)     pos word 0-6     Height              0-127
    heading        pos word 7-9     Direction           0-7
    fine y         pos word 10-12   Tile Pos Y          0-7
    fine x         pos word 13-15   Tile Pos X          0-7
    quality        word 3 bits 0-5  Quality             0-63
    next           word 3 bits 6-15 (Adress: next)      object index
    owner          word 4 bits 0-5  Owner               0-63
    link           word 4 bits 6-15 Quantity/Special    0-1023

  The item id
    Says what the object is (chapter 14 lists them). Bits 6-8 are the major class, bits 4-5
    the minor class, bits 0-3 the item within its class of 16. Traps are 0x180-0x19F and
    triggers 0x1A0-0x1BF (chapters 8 and 9). What each item id is and does is fixed in the
    games' code (chapter 13).

  Flags (bits 9-11) and the enchanted bit (bit 12)
    The editor shows these as two fields, but the game reads bits 9-12 together as one 4-bit
    value, OBJ_FLAGS (0-15) [include/object.h]. Flags 0-7 plus 8 when Enchanted is ticked
    gives that value. What the four bits mean depends on the object:
    - an ordinary item: the enchanted bit says that its link is an enchantment (a special
      property, see "link" below); bits 9-11 are unused on most items;
    - a trigger: four separate switches: bit 9 (UW2) objects and nobody can set it off, bit
      10 it keeps its trap, bit 11 the player can set it off, bit 12 (enchanted) critters
      can set it off (8.3);
    - a trap: the four bits together count the triggers that point at it, 0-15 (8.4). A
      count of 8 or more sets the trap's enchanted bit; that is correct and expected;
    - a lock (0x10F): bit 9 is "locked", bit 10 "can be locked again" (7.4);
    - an eight-position lever or switch (0x161, 0x162): the position, 0-7;
    - writings, gravestones, bridges and pillars: which picture is shown;
    - a book or scroll: bit 10 makes it play a cutscene (both games); UW2: on a red potion,
      bit 11 lets hack trap 38 spoil it (9.7).

  Door (bit 13)
    The record's "doordir" bit. It does two things in the game's code:
    - The game never culls an object with this bit set. Culling is how the game makes room:
      for example when the player arrives by teleport and no free square is found near the
      destination, objects there may be deleted ("punted"); objects with the bit, or holding
      one, are kept [obj/OBJECTS.C chkTenacious, Obj_Elem_Fate]. The shipped triggers and
      traps have it set.
    - UW1: an object with the bit can't be damaged at all, so a door with it is
      indestructible [combat/DAMAGE.C damage_object]. The door panel's "Indestructible"
      toggle sets this bit. UW2 makes the same test for every object except doors, so in UW2
      the bit does not protect a door (from the code; the toggle still sets the bit). Also
      UW2: a broken chest or barrel with the bit does not spill its contents.

  Invisible (bit 14)
    The object is not drawn. Triggers and traps are always invisible in the shipped levels.
    UW2's hack trap 39 changes this bit on another object, which is how a hidden object is
    made to appear (12.1).

  Is quantity (bit 15) and the link (Quantity/Special)
    The link field (10 bits) means one of three things:
    - Is quantity clear: the link is the index of the first object INSIDE this one: a
      container's or a critter's contents, a door's lock and door traps, a lever's trigger,
      a trap's next trap or template. Those objects form their own list through their
      "next" fields. 0 means empty.
    - Is quantity set, link below 512: a quantity. A stack of 5 arrows has link 5. Single
      objects normally have 1.
    - Is quantity set, link 512 or more: a "special property", link - 512: an
      enchantment, the text number of a book or scroll, the key number of a lock, and so
      on. The panel shows it as "Special" (0-511) and adds the 512 for
      you.
    Triggers and delete object traps are the exception: the shipped levels give them Is
    quantity set and the index of their target object in the link (a reference, not
    contents). The game follows a trigger's link whatever Is quantity says (8.1).
    Never change Is quantity or the link by hand on an object that holds something: the game
    would read the old contents as a count, or a count as an object index.

  Heading (Direction)
    0-7, eighths of a turn: 0 north (+y), 2 east (+x), 4 south (-y), 6 west (-x), so 1 is
    north-east and so on, clockwise (inferred from the movement code [sys/UTIL.C move_along];
    every aimed trap in the shipped levels agrees). Levers, switches and writings use it to
    point at their wall (a lever on the west wall, fine x 0, has heading 6; the editor's "Snap
    to nearest wall" does the same); traps use it as a parameter.
    For an item, the game uses the heading to remember what the player has learnt about it
    with the Lore skill: bit 2 means it has been examined, bits 0-1 hold the best lore result
    (3 = identified) [ui/INTERACT.C inv_look]. So heading 7 means "examined and identified":
    it shows its enchantment and charges at once. The "Identified" toggle sets 7.

  Fine x, fine y (Tile Pos)
    The object's place inside its square, 0-7 on each axis (3, 3 is near the middle). Doors,
    levers and wall decorations use them to sit on a wall face. Many traps use them as
    parameters instead (chapter 9), so moving a trap with the mouse keeps them.

  Z (Height)
    Height above the bottom of the map, 0-127. One step of tile height is 8 units, so an
    object lying on a floor of height 4 has z 32, and the highest floor (15) is z 120.
    Triggers and traps use z as a parameter: a look trigger's Search difficulty, a timer's
    interval, a teleport's level, a change terrain trap's new height, and so on.

  Quality
    For items, the condition (0-63, worn out to broken); for doors, hit points (7.4); for a
    critter, the x of its home square (7.5); for triggers, the x of the target square; for
    traps, a parameter.

  Owner
    For ownable items, the race that owns it (taking it is theft to that race); for keys, the
    key number; for a critter, the y of its home square; for triggers, the y of the target
    square; for traps, a parameter.

7.3) Quantity, special properties and links in practice
  - To make a stack, use the "Quantity" box (1-511).
  - Enchanted weapons, armour, rings, wands, potions and scrolls get their effect from the
    "Enchantment", "Effect" or "Spell" list, which writes the special property. A wand or a
    treasure that casts holds a separate spell object (0x120) inside instead.
  - A potion or scroll may instead hold a trap ("Potion trap", "Scroll trap"): the game sets
    off a plain trap held by an object when the object is used, then deletes the trap (8.2).
    The UW1 red potion on level 2 that poisons is built this way.
  - A stack, or an item with a special property, can't hold anything: its link field is
    already used. The editor refuses to add a trigger to one.

7.4) Doors and locks
  Doors are items 0x140-0x147 (closed) and 0x148-0x14F (the same doors open): 0x140-0x145
  ordinary doors, 0x146 portcullis, 0x147 secret door. The door's texture comes from the
  level's door list ("Door type" in the panel).

  How strong a door is
    - Quality is the door's hit points. Damage is first divided by the door type's toughness
      from COMOBJ.DAT, and then taken off the quality; at 0 the door breaks open.
    - Toughness in the shipped UW1 COMOBJ.DAT (measured): 0x140 none; 0x141, 0x142 damage
      halved; 0x143, 0x144 and the secret door 0x147 quartered; 0x145 (the last ordinary
      door, the "massive" door) and 0x146 (portcullis) can't be damaged at all. The Object
      Editor shows and changes these tables.
    - UW1: the "Indestructible" toggle (the Door bit, 7.2) makes any door unbreakable.
    - Owner bit 0 marks a door spiked (the player used a spike on it): in UW1 critters can't
      open it, and looking at it says "The door is spiked." A spiked door keeps its
      strength in the rest of the owner field and is worn down but not broken
      [combat/DAMAGE.C].

  Locks
    A lock is object 0x10F held inside the door (or a chest). Use "Add lock" in the door's
    panel; "Door lock" then selects or destroys it.
    - Locked: bit 9 of the lock's flags. A key that fits locks and unlocks it; locking works
      only on a closed door.
    - "Key ID" (1-63): the lock's special property. A key whose owner (its "Key ID") is the
      same number fits. With "Opened by key" off, no key fits.
    - "Lock difficulty" is the lock's z: picking rolls the Picklock skill against z x 3.
      z 14 also needs Picklock 31 or more (UW2 32), z 15 can't be picked at all
      [obj/USEITEMS.C checkLock, UW2 obj/OBJUSE.C].
    - When a lock opens (picked, by its key, or by the Open spell) the door's unlock triggers
      fire, and then the lock is deleted, unless bit 10 of its flags is set: then it stays,
      unlocked, and the key can lock it again.
    - A door trap can replace or remove a door's lock (9.12). Shipped "lever-only" doors have
      a lock no key fits, and door traps that put the same lock back each time.

  Door traps and door triggers
    - "Add door trap" puts a door trap (0x188) inside the door, after its lock. A door trap
      does nothing on its own: it runs when a trigger links to it. Right click a trigger,
      "Link trigger", and click the door: the editor links to the door's door trap (or asks
      which, when there are several). See 9.12 and the recipe in 11.10.
    - Open, close and unlock triggers go inside the door too (right click the door, "Add
      trigger"). UW1 looks only at the FIRST trap-class object inside a door (8.2): keep the
      lock first, then the trigger, and the door traps after it. The editor adds new objects
      at the END of the door's list, so in UW1 add the door's trigger BEFORE its door traps.
      UW2 runs every trigger in the door.
    - Doors close by themselves now and then while the player sleeps (10.4), unless the
      door's tile has bit 1 of its door byte set.

7.5) Critters
  Critters are items 0x40-0x7F, mobile objects (index 0-255). Placing one with the editor puts
  it in the level's active list, which is what makes the game run its AI (Objects > Level
  Objects shows active critters in green). A critter that is not on the map and not in the
  active list does nothing until something copies it: that is a template (below).

  The Basic tab shows:
  Attitude   0 hostile, 1 upset, 2 mellow, 3 friendly. Hostile critters attack.
  Goal       what the critter is doing now. The names the game's source gives them
             [critter/AI.C critter_mv; uw1/src/include/critter.h]:
               0   stand, watching for the player
               1   go home (to its home square), then mill about
               2   wander at random
               3   UW1: follow its target, jumping to it from afar. UW2: no AI of its own
                   (the critter is moved by other code)
               4   guard: watch, and attack what comes near
               5   attack its target
               6   flee its target
               7   stand (as 0)
               8   mill about near home (what a new critter does)
               9   fight back when cornered
               10  come and talk to the player
               11  drift at random, not reacting to blows
               12  stand at home (hover)
               UW2 also uses 15 (stand frozen while a counter runs down). Other values only
               slow the critter down. The goal target (1 = the player) is not shown by the
               editor; goals 3, 5 and 6 need one, so set them from a trap, a schedule or a
               conversation rather than as a starting goal.
             The editor's goal list calls 2, 4 and 8 "Wander" and 0, 7, 11, 12 "Stand"; the
             meanings above are the exact ones. For a critter that waits and then attacks,
             use 4 (guard) or 0/7 (stand) with attitude 0. For an NPC who walks up and
             speaks, 10.
  HP         its hit points (one byte, 0-255).
  Is NPC / NPC name   the conversation it uses (its "whoami", NPC ID in the Advanced tab).
             0 is none. Several plot rules look at the whoami (10.3), and so do schedules
             and some traps.

  The Advanced tab adds:
  Quality / Owner   the critter's HOME square (x, y): where goal 1 sends it, where goal 8
             mills about and goal 12 stays [critter/AI.C: myxhome = quality]. The editor
             sets it to the square where you place the critter.
  Home (X / Y)  despite the name, the game keeps this word up to date as the critter's
             CURRENT square (the physics and combat code read and write it as its
             position). The editor sets it to the square where the critter lies. For a
             template it matters: a create object trap checks for other created critters
             around this square (9.11), so set it to the square where the copy appears.
  The record also has fields the editor does not show, among them the goal target, the
  "temporary" bit (set on the copies wandering monster spawners make, and on some copies made
  by UW2 plot code; the create object trap's crowding test counts only temporary critters,
  9.11) and the "loner" bit (not affected by race-wide attitude changes).

  Templates
    A create object trap makes a copy of the object it holds, its template (9.11). For a
    critter template:
    - Use "Add template" in the create object trap's panel: the editor makes the critter
      inside the trap, off the map and out of the active list.
    - Every field is copied: hit points, goal, attitude, whoami (so a created NPC can talk),
      home square, Home word, heading and z. The copy appears on the trap's target square at
      the template's fine x/y and z, so set z to that square's floor height x 8.
    - A template may hold ONE object (a key, a weapon): only the first object inside the
      template is copied into the new critter, with nothing inside it.
    - Templates of shipped ambushes are never temporary; the copies of wandering monster
      spawners are made temporary by the game (9.11).

  Critters and triggers
    A critter's death fires no trigger in UW1; its belongings are dropped. UW2: use
    triggers among a dead critter's belongings fire as they fall out, as if used by the
    player (8.6). Critters set off move triggers (and UW2 enter and exit triggers) only
    when the trigger allows critters (8.3); UW2 pressure plates always act as the player,
    whoever presses them (8.7).


8) TRIGGERS
-----------

8.1) What a trigger is
  A trigger is an invisible object that waits for one kind of event: being walked into, the
  object it sits in being used, looked at, picked up or opened, a timer, a schedule. When its
  event happens, and the trigger allows whoever caused it (8.3), it sets off its trap: the
  object its link points to. That trap does its work, and the traps linked after it follow
  (a "chain", 9.1). Traps never go off by themselves (except wandering monster spawners and a
  plain trap held by an item, 8.2 and 9.11).

  The fields of a trigger:
  Quality, owner   the TARGET SQUARE (x, y): the square where the whole chain runs. An arrow
                   trap fires from it, a create object trap places its copy on it, a door
                   trap acts on the door there, a change terrain trap starts its rectangle
                   there, and so on. It does not have to be where the trigger lies: a lever
                   on one wall can open a door at the other end of the level.
  Link             the first trap of the chain (its object index).
  Flags, enchanted who can set it off, and whether it is kept after use (8.3, 8.4).
  Z                normally the floor height x 8. A look trigger uses z as a Search
                   difficulty (8.3), a UW2 timer as its interval (8.8), a UW2 pressure plate
                   must be at the height of what presses it (8.7).
  Fine x, fine y   where it lies in the square (a move trigger catches movers there). UW2
                   pressure plates keep their state in fine y (8.7).

  Where the trap lies
    In every shipped level, the trap a trigger links to lies in the object list of the
    trigger's target square, or inside an object there (door traps sit inside their door).
    The trigger itself has Is quantity set, so its link is a reference and not its contents
    (292 of 292 UW1 triggers, measured). The game depends on this when a used-up trigger's
    trap is deleted: it looks for the trap in the target square's list [event/TRIGGER.C
    delete_trap]. Traps may lie inside solid rock; the player never meets them.

  Linking in the editor
    - Right click the trigger and choose "Link trigger" (or press "Create new link" in its
      panel), then click the trap. Clicking a door links to the door's door trap (the editor
      asks which one when the door has several). This makes the shipped arrangement: the
      trigger keeps Is quantity, its link becomes the trap, its target square becomes the
      square of the trap you clicked, and the trap's trigger count is updated (8.4). Use
      this for every trigger.
    - "Add next trap / trigger" in a trigger's panel creates a new trap INSIDE the trigger
      instead (Is quantity cleared). The game runs it, but it is not how the shipped levels
      are built; 13.3 explains the consequences. It is the right tool for the steps AFTER the
      first trap: a trap's link is its own private list (9.1).
    - "Use target = this tile" sets the target square to where the trigger (or the object
      holding it) lies. "Target square X (quality)" and "Y (owner)" set it directly.
    - Linking a trigger that already holds objects destroys them (the editor warns).

8.2) Where each kind of trigger must be placed
  The game looks for triggers in two places, so a trigger in the wrong one never fires.

  On the tile (in the square's object list):
    - move triggers, both games;
    - UW2 enter, exit, pressure and pressure release triggers;
    - UW2 scheduled triggers: on the square the schedule row names (8.9);
    - UW2 timer triggers: the game finds them through the level's timer list, wherever they
      lie; the shipped ones lie on tiles (8.8).

  Inside the object acted on (right click the object, "Add trigger"):
    - pick up: inside the item that is picked up;
    - use: inside the lever, switch, button, or any object that is used (food, a wand, a
      book...); also fires when a static object is destroyed by damage;
    - look: inside the object looked at: wall decorations (the special texture object
      0x16E painted on a wall face), orbs, debris, any object;
    - open, unlock, UW2 close: inside the door (or chest).

  UW1: the first-trap-object rule
    When an object is acted on, UW1 looks at ONLY THE FIRST trap-class object (trap or
    trigger) in its contents [obj/USEITEMS.C checkTrap]. If it is a trigger, it receives the
    event; if it is a plain trap (not a trigger) whose trigger count is 0 and the event is a
    use, the trap runs at the object's square and is then deleted (this is how a poisoned
    potion works). Anything after it is never looked at. Locks are not trap-class and are
    skipped. So in UW1:
    - an object can hold one trigger that works (two only in a switch, below);
    - in a door, keep the lock first, then the open or unlock trigger, then the door traps:
      a door trap ahead of the trigger hides it.

  UW2: every trigger in the object
    UW2 walks all the trap-class objects in the contents in order: every trigger whose kind
    matches the event fires, then the next. A plain trap met there (count 0, on use, not a
    door trap) runs, is deleted and ends the walk [obj/OBJUSE.C checkTrap].

  Switches and buttons (items 0x170-0x17F, both games)
    Using one first flips it between its "off" item (0x170-0x177) and its "on" item
    (0x178-0x17F), then sends the use event to its triggers. If the switch is now on and
    its first trigger has another object after it, the event passes on to that next trigger
    instead [event/TRIGGER.C UseTrigger]. So:
    - one use trigger: it fires every time, on and off;
    - two use triggers [A, B]: turning it on fires B, turning it off fires A. Keep at most
      two. The second must be a trigger. No shipped UW1 switch has two.
    The editor's lever panel shows only the first trigger. To add the second, right click
    the switch and choose "Add trigger" again: the editor adds it after the first.

  Eight-position levers and switches (0x161, 0x162)
    Using one steps its position (its flags, 0-7, wrapping to 0) BEFORE its use trigger
    fires. Hack traps 3 and 4 read the new position (9.7). The panel's "Position" slider is
    the starting position.

8.3) Who can set a trigger off
  The game passes every event with "who" caused it: the player, a critter, an object (a
  thrown item, a missile, a moving object), or nobody (game code acting on its own: a
  schedule, a conversation opening a door, doors closing while you sleep). The trigger's
  bits decide [event/TRIGGER.C UseTrigger]:

  The player       needs bit 11 ("The player can set it off").
                   A look trigger whose z is above 0 also needs a Search roll: Search - z +
                   a random 0-30 must be above 15, so the chance is (15 + Search - z) / 31:
                   certain when z <= Search - 16, impossible when z >= Search + 15. z is
                   the raw field, not a height above the floor. The Reveal spell rolls with
                   Search 45. Shipped UW1 look triggers use z 0 (most), 3, 7, 8, 10 and 96.
  A critter        needs the enchanted bit ("Creatures can set it off"). The game also tests
                   whether the trigger itself is of the door class, which a trigger never
                   is, so that test has no effect: triggers inside doors work for critters.
  Anything else    UW1: goes off UNLESS the trigger is enchanted and lacks bit 11. So a
  (objects,        thrown object sets off almost any UW1 trigger (188 of the 189 shipped
  nobody)          move triggers), and a critters-only trigger ignores objects. Bit 9 means
                   nothing on a UW1 trigger.
                   UW2: needs bit 9 ("Objects and nobody (...) can set it off"). UW2 code that acts
                   as nobody: scheduled triggers (always), door triggers fired by a
                   conversation's HandleDoor, by doors closing by themselves (sleep, schedule
                   hack 4), by a closing door bumping into something and reopening, and the
                   switches flipped by hack trap 18.
  Always the       UW2 pressure, pressure release and timer triggers act as the player
  player           whoever or whatever pressed the plate, so they need bit 11.

  Reached along a chain (a trap linking to a trigger), by a failed disarm, or by special
  plot code (8.10), a trigger is called with mode -1: no event test and no who test at all.

  The usual settings (Flags value, plus the enchanted bit):
    Flags 6, not enchanted    the player, repeatable. The editor's "Unlimited".
    Flags 4, not enchanted    the player, once. The editor's "One time only".
    Flags 6, enchanted        the player and critters, repeatable.
    Flags 4, enchanted        the player and critters, once (the UW1 level 2 minefield).
    Flags 0, enchanted        critters only, once (the UW1 Rune of Warding).
    UW2 flags 1               objects and nobody, once (one-shot scheduled triggers).
    UW2 flags 5 / 7           objects, nobody and the player, once / repeatable.

  The trigger panel has a toggle for each: "The player can set it off" (bit 11), "Creatures
  can set it off" (enchanted), the toggle that keeps the trap after use (bit 10, 8.4), and
  in UW2 "Objects and nobody (...) can set it off" (bit 9).

8.4) Used up or kept, and the trap's trigger count
  Bit 10 ("keeps its trap") decides what happens after the trigger has run its chain.
  - Set: nothing; it can fire again.
  - Clear: the game deletes the trap at the target square together with everything its
    link reaches (the whole chain after it), every OTHER trigger on the level that links
    to that trap, and the trigger itself [event/TRIGGER.C UseTrigger, delete_trap].
  This happens WHATEVER THE CHAIN DID. A check variable that did not match, a create object
  roll that failed, an inventory trap whose item was missing, a teleport that found no
  room: the one-shot trigger and its chain are gone all the same. Give bit 10 to every
  trigger meant to retry until something succeeds, and use a set variable trap to remember
  that it has succeeded (11.9).

  When a chain reaches another trigger, that trigger runs its own trap at its own target
  square and then applies ITS OWN bit 10 rule to that trap (9.1).

  The trigger count
    A trap's flags (bits 9-12, 0-15) must equal the number of triggers that link to it. The
    game uses the count to find and remove those triggers when the trap is deleted: it
    scans the whole map until it has removed that many.
    - Too low: some triggers are left behind, linking to the freed trap. Later they run
      whatever object reuses that slot as if it were a trap (inferred from the code).
    - 0 with a one-shot trigger: no search is made, and the trigger stays behind, linking
      to the freed slot. Also, a create object trap with count 0 and a critter template is
      a wandering monster spawner (9.11), so don't leave a triggered one at 0.
    - 8-15: the count's top bit is the trap's enchanted bit. That is correct (a shipped UW1
      level 7 trap has 15 triggers).
    The trap panel shows how many triggers point at it and the count (0-15), and fixes the
    count on a click; linking with "Link trigger" updates it; Tools > Fixes checks every
    trap. The game reads the count only on the first trap of a chain (the one a trigger
    links to). Chain steps made with "Add next trap / trigger" get count 1, which is
    harmless; leave it. Do NOT set a chain-step create object trap with a critter template
    to 0: at 0 it also becomes a wandering monster spawner (9.11). A create object trap
    placed with "Add trap" starts at 0, so it is a spawner until a trigger is linked to it.
  UW1 bug: in any one object list (a tile or a container), the game stops removing at the
  first trigger it removes there, so a second one-shot trigger for the same trap later in
  the same list survives (13.4).

  A single trigger can also be removed by a disarm (10.6), by the destruction of the object
  holding it, or by a delete object trap. When the game frees it as part of its holder's
  contents (both games) or with a UW2 delete object trap, it lowers the trap's count by one,
  or deletes the trap when it was the last trigger [trigger_obj_del, trap_obj_del;
  obj/OBJECTS.C Obj_FreeChain]; a UW1 delete object trap aimed at the trigger itself does not
  change the count.

8.5) UW1 trigger kinds (0x1A0-0x1A6)
  The kind of event each trigger waits for comes from a table in OBJECTS.DAT [event/TRIGGER.C
  trap_init]. In the shipped table:

    Item   Name      Event comes from                                   Placed     Shipped
    0x1A0  move      walking or colliding into it                       tile       189
    0x1A1  pick up   taking the item it is in from the 3D view          in item     17
    0x1A2  use       using the object it is in                          in object   56
    0x1A3  look      looking at the object it is in                     in object   24
    0x1A4  step on   NOTHING: no code sends this event, it never fires  -             0
    0x1A5  open      the door it is in starting to open                 in door      6
    0x1A6  unlock    the lock of the door it is in opening              in door      0

  0x1A0 move (who: the mover)
    - Fires when the player, a critter, a thrown object or a missile collides with it, and
      after every step the player takes with the step keys.
    - Only move triggers have a collision volume (radius 2, height 32, from COMOBJ.DAT), so
      they are the only triggers that anything walks into. Put them on the tile, z = the
      floor height x 8, fine x/y where the player should be caught.
  0x1A1 pick up (who: the player)
    - Fires when the player takes the item from the 3D view, before it leaves its tile.
    - Taking it from a bag, from the inventory, or from an NPC fires nothing.
  0x1A2 use (who: the user)
    - Fires after the object is used (from the view, the inventory, by a pole on a button),
      after food is eaten, after a wand or an enchanted book or scroll is used, and when a
      static object on the map is destroyed (who = the attacker).
    - A thrown object hitting a usable object (buttons are usable; doors and levers are
      not) uses it, so it can press a button (inferred from the code).
  0x1A3 look (who: the player)
    - Fires when the player looks at the object in the view or the inventory, and when the
      Reveal spell finds the object (8.3 for the Search roll).
    - Looking in the inventory sends the event before the game has worked out which
      object is under the cursor, so a look trigger in a carried object may not fire
      (a bug in the game) [ui/INTERACT.C inv_look].
  0x1A4 step on
    Never fires. Use a move trigger.
  0x1A5 open (who: the opener)
    - Fires when a closed door at rest starts to open, whoever opens it: the player, a
      critter, a door trap, a conversation's HandleDoor. A moving door turned round fires
      nothing, and UW1 has no close trigger.
    - Special case: the Key of Infinity (0xE7) used on a special texture object (0x16E)
      that shows a door texture fires the open trigger inside that object.
  0x1A6 unlock (who: the user)
    - Fires only when a LOCKED lock opens: picked, by its key, by the Open spell, or by a
      critter picking it. Locking with a key fires nothing; a door without a lock never
      fires it.

8.6) UW2 trigger kinds (0x1A0-0x1AF, 0x1B0-0x1BF)
  UW2 has 13 named kinds. Each comes in two forms with the same behaviour: 0x1Ax and 0x1Bx.
  The only difference is that 0x1Bx triggers can be FOUND and DISARMED by the Search and
  Traps skills and the Detect Trap and Remove Trap spells (10.6); 0x1Ax ones can't.

    Items        Name             Placed              Who it sees
    0x1A0/1B0    move             tile                the mover
    0x1A1/1B1    pick up          in the item         the player
    0x1A2/1B2    use              in the object       the user
    0x1A3/1B3    look             in the object       the player
    0x1A4/1B4    pressure         tile (8.7)          always the player
    0x1A5/1B5    pressure release tile (8.7)          always the player
    0x1A6/1B6    enter            tile, first (8.7)   the mover
    0x1A7/1B7    exit             tile, first (8.7)   the mover
    0x1A8/1B8    unlock           in the door         the user
    0x1A9/1B9    timer            anywhere (8.8)      always the player
    0x1AA/1BA    open             in the door         the opener, or nobody
    0x1AB/1BB    close            in the door         the closer, or nobody
    0x1AC/1BC    scheduled        tile (8.9)          nobody
    0x1AD-0x1AF, 0x1BD-0x1BF      unnamed: their table entry is 0, so they behave as move
                                  triggers (measured)

  Move, pick up, use, look and unlock work as in UW1 (8.5), with these differences:
  - Move: the player's step keys set off only item 0x1A0; a 0x1B0 move trigger fires only by
    collision.
  - Use: triggers among a dead critter's belongings, or in a container emptied onto the
    floor, fire as they fall out, as if used by the player [obj/TREASURE.C]. Hack trap 18
    uses a switch as nobody.
  - Look: the Reveal spell fires the first 0x1A3 inside its target (with Search 45).
  - A trigger lying on a tile is not inside any object, so the skills that find triggers
    in objects can't find it, even a 0x1Bx one (inferred from the code).

  Open (0x1AA) fires when a closed door starts to open, when a moving door is turned round
  to open, and when a closing door finds something in the doorway and turns back (as
  nobody). Close (0x1AB) fires when an open door starts to close, or a moving door is turned
  round to close; doors that close by themselves (sleep, schedule hack 4) and a
  conversation's HandleDoor fire it as nobody, so such triggers need bit 9.

8.7) UW2 enter, exit and pressure plates
  When the player or an object moves to another tile, the game sends "exit" to the old tile
  and "enter" to the new one. A change of height within a tile, picking an object up, a
  missile landing and an object coming to rest send the pressure events directly
  [event/TRIGGER.C check_pplate, update_pplate].

  Enter and exit triggers
    - Only the FIRST trigger in the tile's object list is tested as an enter or exit
      trigger; it fires if it is of the right kind, with the mover as "who". After it, the
      event becomes "pressure" (for enter) or "pressure release" (for exit) for the rest of
      the list.
    - So an enter or exit trigger must be the first trigger on its tile. Six shipped ones
      are not, and never fire.

  Pressure plates (0x1A4/0x1B4 pressure, 0x1A5/0x1B5 release)
    A plate fires when the weight on it crosses a threshold:
    - Its z must EQUAL the height at which the event happens (the floor height x 8 for
      the player walking onto a flat tile); a plate at another z is skipped.
    - Fine y bit 0: its state, 1 = pressed. Set it to 0 when placing a plate.
    - Fine y bit 1: when it changes state, the tile's floor texture steps up by one
      (pressed) and back down (released), so the plate visibly sinks: put the "pressed"
      texture right after the plate's in the level's floor textures (inferred).
    - Fine y bit 2: heavy plate, threshold 84 instead of 4. The weight counted is everything
      on the tile at the plate's height: mass x quantity, with containers' contents, and
      for the player his own weight plus what he carries and holds (tenths of a stone,
      inferred from the inventory panel).
    - Fine x is not used.
    - An unpressed plate fires on a pressure event when the weight is now above the
      threshold; a pressed plate fires on a release event when it is not. Every plate on
      the tile then flips its state. If nothing fired, but the weight test passes against a
      plate of the other kind, the plates flip without firing.
    - Plates always act as the player: give them bit 11, and bit 10 to fire on every step.
    - An object coming to rest is tested at height 0 (a slip in the game: only plates at z
      0 notice an object dropped on them that way; inferred).
    The Tomb of Praecor Loth's plates (12.10) use fine y 6: heavy, floor texture steps.

8.8) UW2 timer triggers
  A timer trigger (0x1A9/0x1B9) fires on its own, again and again, while the player is near.
  - The interval is its z: it fires every (z + 1) / 4 seconds of game time. The game
    counts quarter seconds from 0 to 127 and then wraps, and fires a timer each time the
    count passes a multiple of z + 1; when z + 1 does not divide 128, one gap per 32
    seconds is shorter. Examples: z 3, every second; z 7, every 2 s; z 27, about every 8 s.
    For z + 1 above 64 that does not divide 128, it fires only once every 32 seconds
    (inferred from the arithmetic).
  - It fires only while the player (or the eye of Roaming Sight) is less than 8 squares
    from its TARGET SQUARE on both axes (|dx| < 8 and |dy| < 8). Where the trigger lies does
    not matter for this.
  - It acts as the player: give it bit 11. Give it bit 10 too, or it fires once and is
    deleted.
  - Nothing fires while time is stopped. The end of a conversation, and doors closing at
    sleep (or schedule hack 4 with argument 0), each run 8 extra ticks, so timers fire then
    too.
  - The timer list: each level keeps a list of up to 64 timer triggers, and only listed
    triggers fire. The game never adds to it while playing (nothing calls its add
    function), so a timer can't be created by a trap. The editor writes the list for you
    when it saves a UW2 level: every timer trigger on the level is listed, in its old place
    if it had one [Data/LevArk.cs WriteUw2Timers]. A level with more than 64 timers gets a
    warning and the extra ones never fire.

8.9) UW2 scheduled triggers
  A scheduled trigger (0x1AC/0x1BC) is fired by a schedule row with event 5 (10.5): the row
  names a square (byte 5, byte 6), and the game fires EVERY scheduled trigger in that
  square's object list on the current level, as nobody [event/SCDEVENT.C ev_trigger].
  - Give it bit 9 (every shipped one has it). Bit 10 decides whether it can be fired again:
    flags 1 or 5 once, 7 every time.
  - Its quality/owner are the target square as usual, so one "bus" square can hold several
    scheduled triggers, each aimed at a different trap anywhere on the level (12.1).
  - "Who" is nobody, so traps that act on who do nothing useful in such a chain: teleport,
    damage, proximity, and hacks 3, 4, 30, 41, 42 and 62.
  - UW2 also fires the scheduled triggers on square (15, 29) of the current level (the
    castle, level 1, in practice) when a castle person (whoami 0x81-0x8F, Syria 0xA8, guard
    0x95) would be killed: for each one, the object its trap links to (a guard template)
    gets the attack site as its home, goal 1, and is made temporary and powerful, and then
    the trigger fires [event/WORLDEV.C call_out_the_guards]. The game treats every object
    after the first scheduled trigger in that list as one, so keep only scheduled triggers
    there (inferred).

8.10) Other ways a chain starts
  - A plain trap held by an object (no trigger, count 0) goes off when the object is used,
    at the object's square, and is deleted (8.2).
  - A failed disarm sets off the trap (10.6).
  - UW1: using Garamon's bones on his grave fires the first object on square (54, 52) of the
    current level as a move trigger set off by the player (10.3, 12.7).
  - UW2: fire_trigger_at(x, y) fires the first trap-class object on a square of the current
    level, a trigger with mode -1 or a trap directly, as nobody. It is used by Bliy Skup
    Ductosnore's death (58, 18) and (60, 18), Praecor Loth's death (1, 2), hack trap 25 (58,
    5), going to jail (39, 37), and leaving level 10 (Prison Tower level 2): (31, 36) and
    (35, 34) [event/WORLDEV.C, game/GAMEWRAP.C do_level_hacks].
  - Wandering monster spawners are run directly by the clock and by sleep (9.11).
  - Wards on a wandering monster's path are run directly while the player sleeps (10.6).


9) TRAPS
--------

9.1) How a chain runs
  Traps are objects 0x180-0x19F that do something to the world: hurt, move the player, change
  tiles, create or delete objects, open doors, test and set variables. Most are not "traps"
  in the everyday sense. A trap runs only when a trigger (or a trap before it) sets it off.

  1. A trigger sets off its trap at the trigger's TARGET SQUARE (written "x, y" below). The
     game remembers for the whole chain who set it off ("who") and the object acted on
     (the lever, the door...).
  2. The trap does its work (9.4 onwards).
  3. Unless that trap ends the chain, the object its link points to runs next, if it is a
     trap or a trigger:
     - a trap runs at the same square x, y;
     - a trigger runs with mode -1 (no event and no who test, 8.3): its own trap runs at
       ITS OWN target square, and afterwards its own bit 10 rule applies to that trap
       (8.4). This is how one chain acts on several squares;
     - any other object ends the chain.
  4. The chain ends when a trap ends it or has no link.

  A trap's link is a private list, like a container's contents: the next trap of a chain
  lies INSIDE the previous one, not on any tile (so are the shipped levels' chains in both
  games, measured). In the editor, select
  the trap and use "Add next trap / trigger" in its panel; that creates the next step inside
  it. Only the first trap of a chain lies on the map (on the trigger's target square).

  Traps that END the chain:
    - create object (always, even when it created nothing);
    - delete object;
    - ward, and UW1's tell;
    - door: UW1 always; UW2 when its owner is not 0 and a door was found;
    - UW1 inventory, when the item is missing or the stack too small;
    - a condition trap that takes its other branch (9.2).
  So put a create object, delete object or door trap LAST in a chain. A chain is a single
  line: when a step is a trigger, that trigger's own chain takes over and nothing of the
  outer chain follows it. To make several chain-ending things happen at once, give each its
  own trigger: several move triggers on one tile all fire, and UW2 fires every trigger in an
  object and every scheduled trigger on a square.

  Traps that use their link as DATA, not as the next step: create object (the template),
  delete object (the object to delete), door (the lock to put on the door), UW2 change from
  (its change to), and the UW2 hacks 4, 21, 22, 23, 27, 28, 39 and 62 (the object they act
  on). The hacks still continue the chain through that link, so if the object they act on
  is itself a trap or trigger, it runs next.

  Two cautions:
  - There is no loop guard. A chain that links back to an earlier step runs for ever and
    the game hangs.
  - When a step starts a chain of its own (a door trap opening a door that holds an open
    trigger; UW2 hacks 18 and 25), the game forgets "who" for the rest of the outer chain
    afterwards. A teleport or damage trap after such a step then does nothing [event/
    TRIGGER.C SetOffTrap] (inferred from the code). Put those before it.

9.2) Condition traps and the "else" branch
  A condition trap tests something. When the test says "go on", the chain continues
  through its link as usual (the "then" branch is the first linked object and the chain
  after it). When it says "branch", the game runs the SECOND object in the trap's link
  list instead (the first linked object's next), and then the chain ends.

    Trap                    Goes on (first object) when     Branches (second object) when
    check variable (both)   the values are equal            they differ
    inventory (UW2)         the item is there (and worn,    any test fails
                            and enough of it, if asked)
    skill (UW2)             the check FAILS                 the check PASSES
    proximity (UW2)         who is inside the area          who is outside it
    UW1 inventory           the item is there               (no branch: the chain ends)

  - UW1: the else object must be a TRIGGER (it runs with mode -1 at its own target square);
    a trap there does nothing. Both shipped else branches are triggers.
  - UW2: the else object may be a trap (it runs at the same square) or a trigger. The game
    does not check that it is either, and would run any other object as a trap of type
    (item id & 0x3F): put only traps or triggers there (inferred from the code).
  - With no link at all, a check variable trap that does not match just ends.
  - UW1's check variable panel has a second "Add next trap / trigger" button: the first
    object you add is the "then" branch, the second the "else". For any condition trap that
    lies on the map, right click it and choose "Add trigger": the trigger is added after
    the first linked object, as the else branch; then press "Create new link" in that
    trigger's panel and click the trap it should set off.

9.3) Reading the descriptions below
  - "x, y" is the square the chain runs at (the trigger's target square), not where the
    trap lies.
  - "who" is whoever set off the chain (8.3); "nobody" for scheduled triggers and other
    game code.
  - Fields not mentioned are unused.
  - In UW1, every trap has its own Basic panel (named below). In UW2, the damage, teleport,
    door and delete object traps use the same panels; the others show their raw fields
    (Quality, Owner, Z, Heading, Fine X, Fine Y) with a line "Now: ..." that decodes them.
  - Real uses from the shipped games are given as level (x, y). UW2 levels are counted as
    the game counts them, 1-80, with the world and the level within it.

9.4) 0x180 Damage trap (both)
  Hurts, or poisons, whoever set off the chain.
  Quality  the amount, 0-63.
  Owner    0: damage. Not 0: poison.
  - Owner 0: who takes "quality" points of damage of type 4 (physical), through armour and
    resistances. Quality 0 does nothing.
  - Owner not 0, and who is the player: he is POISONED at strength "quality", if that is
    above his current poison and he does not resist poison. He takes no damage at once.
    Poison is a 4-bit value, so only strengths 1-15 make sense: 16 stores 0 (no poison at
    all), 17 stores 1, and so on. Poison then hurts him once a minute of game time and
    wears off as it does; strength 4 costs about 4 + 3 + 2 + 1 hit points (inferred). Sleep
    cures it.
  - Owner not 0, and who is anything else: plain damage of "quality".
  - It NEVER heals.
  - Set off by nobody (a scheduled chain), it does nothing useful.
  - The chain continues.
  - A random roll (7 in 10) is made and its result ignored.
  Shipped: UW1 level 3 (1, 10): q 4, owner 1, the poison needles (11.5); level 2 (14, 51): a
  red potion holding q 10, owner 1, which poisons when drunk; level 2 minefield, q 20; level
  7: damage floors of 4 and 40, and lava stepping stones of 3. UW2: 9 poison traps, strengths
  0-12; a cheese on level 9 and two green potions on level 17 hold damage traps.
  Panel: "Damage (or poison strength)", and "Poisons the player (strength 1-15) instead of
  damaging".

9.5) 0x181 Teleport trap (both)
  Moves the player to another square of this level or another level. Stairs between levels
  are teleport traps.
  Quality, owner  the destination square (x, y).
  Z               the destination level: 0 = this level; otherwise the level number (UW1
                  1-9, UW2 1-80).
  - ONLY THE PLAYER MOVES. If a critter or an object sets it off, nothing happens.
  - Same level, and neither coordinate is 63: the game takes the nearest free square to
    the destination, searching the 9 x 9 box around it outwards; if none is free, nothing
    happens.
  - x or y = 63 (0x3F) skips that search.
  - UW1: a destination x of 0 is ignored: the trap never works.
  - The move is only recorded, and made after the chain ends: the level changes if needed,
    and a free square is searched for again, first strictly, then loosely. The loose
    search may delete objects and critters on the squares it looks at (7.2, culling). If
    no square at all is found, the player dies.
  - UW1: fine x/y and heading are unused (UW1 has no facing on arrival).
  - UW2, fine x bits:
      bit 0  arrive near the ceiling and fall (clear: on the floor);
      bit 1  face the trap's heading on arrival;
      bit 2  when the player set it off: he is "lost": the automap switches off until he
             reaches a part of the map that turns it back on.

    teleport out of world 8 is refused; while he is jailed (quest 112), a teleport anywhere
    but the cell (x 42 or 43, y 38, z 0 or 1) is an escape (quest 112 cleared, 124 set); in
    the Pits of Carnage, leaving the arena counts as running from the fight.
  - The chain continues (the move comes afterwards).
  Shipped: UW1 has 63; stairs put the trap on the stair square with the destination at or
  near the same (x, y) on the next level. Level 1 (example): z 2, destination (7, 38).
  Panel: "Teleport in this level", "Target level", "Target X", "Target Y". UW2's fine x bits
  and heading are set in the Advanced tab.

9.11) 0x187 Create object trap (both)
  Makes a copy of the object it holds, its template: ambushes, loot, blockers, spawners.
  Quality  the chance of NOT creating, in 63: it creates with chance (63 - quality) / 63.
           0 always creates, 63 never.
  Link     the template, held INSIDE the trap (Is quantity clear).
  The template's fine x/y and z  where the copy appears inside square x, y.
  1. The chance is rolled. On failure nothing is made and the chain ends.
  2. If the trap has Is quantity set or no link, nothing happens. So always make the
     template with "Add template", never with "Create new link".
  3. Crowding: if the template is a critter, and a TEMPORARY critter (other than the
     player) is within 4 squares of the template's Home square on both axes, nothing is
     made [event/TRIGGER.C dont_create_wandering_monster_here]. The test centres on the
     template's own Home (X / Y) word, not on x, y: set it to the spawn square.
  4. UW2: nothing is made in world 6 (levels 49-56) once Praecor Loth is dead (quest 7).
  5. UW2: a template of item 0x7F (the adventurer) becomes a random monster suited to the
     level, the castle stage and the player's level; the copy is hostile and temporary.
  6. A copy is placed on square x, y at the template's fine x/y and z, with every field of
     the template. If the template holds objects, only the FIRST is copied into the new
     one, empty. An animated object joins the animation list.
  - THE CHAIN ALWAYS ENDS here, whatever happened. Put it last.
  - Shipped ambush templates are not temporary, so ambush copies never block each other:
    a repeatable trigger makes a new copy every time.

  Wandering monster spawners
    A create object trap with trigger count 0 (no trigger) and a critter template is run
    by the game itself [event/TRIGGER.C DoWanderingMonsters]:
    - UW1 every 24 slow updates (8 minutes of game time), UW2 every 30 (10 minutes), each
      time with chance 1 in 4, for spawners 8 or more squares from the player on either
      axis;
    - and every time the player's sleep is not interrupted, for all spawners on the level,
      wherever they are.
    The template is marked temporary, so its copies are temporary and the crowding test
    stops them piling up. The quality still gives the chance per run (shipped spawners use
    29-60 in UW1, 0-60 in UW2). Both games look only at the first create object trap found
    on each square, and the search goes inside objects, so a create object trap that is a
    chain step (inside another trap) with count 0 and a critter template is a spawner too
    [obj/OBJECTS.C Obj_FindInMap]. Shipped: 34 in UW1 (example: level 1 (47, 4), quality
    31), 49 in UW2 (one of them a chain step after a skill trap, level 65 (60, 57)).
    So a create object trap meant for a trigger must keep its trigger count right: at 0 it
    becomes a spawner.

  Shipped: UW1 has 65 create object traps, most with critter templates and quality 0
  (ambushes, 11.2). Level 7 (21, 36) creates a large boulder (a non-critter template)
  behind the player: "You hear rocks falling behind you!". UW2 makes Mors Gotha, soldiers
  and notes this way on plot steps (12.1).
  Panel: "Height", "Spawn chance" (percent; the editor converts it to quality), "Template"
  ("Select", "Destroy") or "Add template".

    continues. There is no else branch.
  - UW2: missing, not worn when asked, or too few: BRANCH (the second object); otherwise
    go on. Always give a UW2 inventory trap a link: the game branches without checking for
    one (null pointer).
  Shipped: UW1 level 7 (20, 42): a crystal splinter (0x111), z 1, makes rocks part (11.14
  shows the UW2 form). UW2 Britannia level 4: the jewelled dagger opens a wall (12.9).
  Panel: "Item to check", "At least this many in a stack (Z, 0 any)".

9.17) 0x18D Set variable trap (both)
  Changes one of the game's variables or quest flags, which other traps, conversations and
  (UW2) schedules can test (10.1).

  UW1
    Value  quality x 256 + owner x 8 + fine y (owner's top bit overlaps quality's lowest).
           For a value 0-63: quality 0, owner = value / 8, fine y = value % 8. The panel's
           "Value / quest index" box does this for you.
    Z      0: a quest bit; 1-63: game variable z.
    Heading  the operation.
    - z 0: quest bit "value" (0-31): heading 5 toggles it, 1 clears it, anything else sets
      it.
    - z 1-63, by heading: 0 add, 1 subtract, 2 set, 3 and, 4 or, 5 xor, 6 shift left,
      7 nothing. The result is kept to 6 bits (0-63), so "set" stores value % 64.
    - Game variable 0 can't be set by this trap (z 0 means the quests). Never use z 64 or
      more: it overwrites other parts of the player's record.
  UW2
    Variable   z + 128 x fine x: a numbered variable 0-415 (10.1); higher numbers do
               nothing.
    Value      quality x 64 + owner (0-4095).
    Heading    the operation: 0 add, 1 subtract, 2 set, 3 and, 4 or, 5 xor, 6 shift left,
               7 "value + 1 if it equals the operand, else 0".
    Fine y     not 0: X clock 15 also goes up by 1, so the schedules' block 15 looks again
               at their next update (10.5).
    - Game variables (0-255) are stored modulo 256.
    - Quest flags (256-383) follow their own rules: operation 5 toggles, 1 leaves the flag
      as it is, any other sets it to 1 if the value is above 0, else 0.
    - Changing an X clock (400-415) does not run the schedules by itself; they catch up at
      the next conversation end, level change or sleep, or at once with hack trap 37.
  The chain continues.
  Panel (UW1): "Set quest variables", "Variable index" (or "Quest bit (0-31)"), "Value",
  "Operation type".

9.18) 0x18E Check variable trap (both)
  Compares one variable, or several in a row, with a value, and branches (9.2).
  Value  ((quality x 32 + owner) x 8) + fine y: the same encoding as UW1's set variable.
  Heading  the number of variables to read, minus 1 (0 = one variable).
  UW1
    - Reads game variables z .. z + heading (here z 0 is variable 0, not the quests).
    - Fine x not 0: they are added. Fine x 0: they are packed, 3 bits each: v = v x 8 +
      (var & 7), like the digits of an octal number.
    - Equal: the chain goes on through the link (a trap or a trigger). Different: the
      SECOND linked object runs, and it must be a trigger; with none, the chain ends.
    - Keep z + heading below 64.
  UW2
    - The first variable is z + 128 x (fine x & 3). Fine x bit 2 (value 4) set: added; clear:
      packed 3 bits each. So a SINGLE variable is compared by its low 3 bits only unless fine
      x bit 2 is set: set it to compare whole values.
    - Equal: go on. Different: branch, if the trap has a link.
  Example (UW1 level 5, levers at (6, 29)): z 31, heading 2, fine x 0, quality 1, owner 26,
  fine y 6: the value is octal 726, so game variables 31, 32 and 33 must read 7, 2 and 6
  for the door at (3, 27) to open.
  Panel (UW1): "First variable (Z)" (0-63), "Variables after it (heading)", "Pack 3 bits of
  each instead of adding",
  "Value checked for", and "Add next trap / trigger" for the else branch.

9.19) 0x18F UW1 combination trap / UW2 null trap
  Do nothing and pass the chain on. None shipped in UW1.

9.20) 0x190 Text string trap (both)
  Prints a message on the scroll.
  Quality, owner  the string quality x 32 + owner of block 9 (the trap texts).
  - UW1 convention (all shipped): each level has its own 64 strings, quality = 2 x (level -
    1), so string 64 x (level - 1) + owner.
  - UW2: only owner & 31 is used, and a string with owner bit 5 set never prints (it
    waits for a player flag nothing sets).
  - The chain continues.
  Panel: "Text": type the message; the editor finds or frees the string itself.

9.21) 0x191 Experience trap (UW2)
  Gives or takes experience points.
  - Amount = (quality x 8 + (owner & 7) - 256) x 2 ^ (owner / 8). Quality below 32 gives a
    loss. Example: quality 57, owner 0: 200 (100 after the halving below).
  - A gain is halved, and halved again (plus 1) when the player's level is above 2 x world
    + 2. A loss can't take experience below 0.
  - The chain continues.

9.22) 0x192 Jump trap (UW2)
  Throws whatever is moving into the air (springboards).
  - It acts on the object being moved by the physics when the chain runs, so put it under a
    move trigger (inferred).
  - It acts only if that object's horizontal speed is at least heading x 47 (heading 0:
    always).
  - Vertical speed becomes quality x 47 / 2 for the player, quality x 141 / 4 for anything
    else; horizontal speed is halved, or stopped if owner is not 0.
  - The chain continues. 25 are shipped (levels 33, 34, 46, 57, 65).

9.23) 0x193 Change from and 0x194 change to (UW2)
  Find-and-replace on tiles: every tile in an area that matches the change from values gets
  the change to values. (They change TILES, not objects.)
  - The change from trap's link must be the change to trap (it lies inside it). Without
    one the game reads a null pointer (inferred).
  - Area: x .. x + fine x - 1 by y .. y + fine y - 1 (fine y 0: the same as fine x); fine x 0
    means the whole map (squares 1-62).
  - Fields, in both traps:
      wall    quality                       63 = any / leave
      floor   heading + 8 x (z bit 4)       15 = any / leave
      type    owner                         10 = any / leave
      height  z bits 0-3                    15 = any / leave
  - A part whose change to value is at its limit is left alone. Otherwise the tile must
    match the change from value (or the change from value is at its limit, "any").
  - The change to does nothing itself; the chain continues into it and on through ITS link.
  Example (12.2): change from wall 0, floor 0 -> change to wall 48, floor 12 gives every
  square of a room that has wall 0 and floor 0 the ice textures, and leaves the rest.

9.24) 0x195 Oscillator (UW2)
  Steps one property of square x, y up or down by one each time it runs: floors that rise
  and fall, bobbing stones (11.12).
  Fine x   bits 1-2 what moves: 0 height, 1 floor texture, 2 wall texture (3: undefined).
           bit 0 the current direction: 1 up, 0 down. The trap rewrites this bit itself.
  Quality  the low limit. Owner  the high limit.
  - The new value is the old one +-1; it is applied only if quality <= new <= owner.
  - Going up and reaching owner, it turns to go down; going down and reaching quality, it
    turns up.
  - For height: a solid tile going down becomes open at 15; an open tile reaching 16
    becomes solid.
  - What stands on the tile rides with it. The chain continues.
  - All 64 shipped oscillators move height, driven by timer triggers.
  - Level 68 (0x44) has a special case for its sunken moongate.

9.25) 0x196 Proximity trap (UW2)
  Tests where "who" stands.
  - Inside means: who's square is within x .. x + quality and y .. y + owner (the area runs
    only towards +x and +y), and its height passes: (fine x not 0 or height <= z) and
    (fine y not 0 or height > z). Both fine x and fine y set: any height.
  - Inside: go on. Outside: branch.
  - Set off by nobody, it reads a null pointer: don't use it in scheduled chains.
  - Always give it a link: the game branches without checking for one (null pointer).

9.26) 0x197 Pit trap (UW2)
  Toggles square x, y between height 0 and a stored height: a floor that drops away and
  comes back (11.13).
  - At height 0: the new height is fine x + 8 x fine y, the floor texture owner.
  - Above 0: the new height is 0, the floor texture quality.
  - A new height above 15 makes the tile solid; otherwise it becomes (or stays) open.
  - The chain continues.

9.27) 0x198 Bridge trap (UW2)
  Lays or removes a row of bridges (0x164).
  - Direction: the heading, rounded down to even and written back into the trap: 0 +y,
    2 +x, 4 -y, 6 -x. It covers "quality" squares from x, y.
  - Owner / 16: 1 lays bridges at the trap's z and heading (unless one is there), with the
    bridge's flags (its picture) = owner & 15; 2 removes them; anything else nothing.
  - The chain continues.

9.28) 0x199-0x19F (UW2)
  No action; the chain continues. 0x19E (flam rune) and 0x19F (tym rune) are trap-class
  items that act when the player uses them, not as part of a chain.


10) HOW TRAPS INTERACT WITH THE REST OF THE GAME
------------------------------------------------

10.1) Variables
  Traps can remember things only through the game's variables and quest flags, kept in the
  player's record (PLAYER.DAT in a save). The same values are read and written by
  conversations and, in UW2, by the schedules, so they are how these parts of the game talk
  to each other.

  UW1
    - 64 game variables, 0-63, each kept to 0-63 by the set variable trap. All start at 0
      except variable 26 (the bullfrog puzzle's moves, 53).
    - 32 quest bits, 0-31 (z 0 on a set variable trap), plus quest bytes 32-35 that only
      conversations reach (32 is the Knight of the Crux).
    Who uses them:
      set variable trap    writes game variables 1-63 and quest bits 0-31 (9.17);
      check variable trap  reads game variables 0-63 (9.18);
      conversations        GetTrapVariable / SetTrapVariable (game variables, built-in
                           x_traps), GetQuest / SetQuest (quests). From a conversation only
                           quests 0-14 work reliably (6.10), while traps can set 16-31.
    Shipped uses: variables 24-26 the bullfrog puzzle (level 4); 16 the level 3 button
    puzzle; 27 the level 4 switch puzzle; 31-33 and 34 the level 5 lever puzzles; 50 is
    set to 1 on level 7 when the portcullis slams shut. Quest bit 7 is set by opening a
    portcullis on level 3.

  UW2: the numbered variables
    One numbering covers everything:
      Numbers    What                          Notes
      0-255      game variables                stored as bytes: results are kept modulo 256
      256-383    quest flags 0-127             one bit each
      384-399    quest bytes, quests 128-143   bytes
      400-415    X clocks 0-15                 bytes (10.5)
      416 up     nothing                       writes ignored, reads give 0
    Operations (set variable trap, schedule events 7 and 9): 0 add, 1 subtract, 2 set,
    3 and, 4 or, 5 xor, 6 shift left, 7 "value + 1 if equal to the operand, else 0".
    Quest flags take their own rules: 5 toggles, 1 leaves the flag alone (in UW1 heading 1
    clears a quest bit!), any other operation sets it to 1 if the operand is above 0, else
    to 0 (so "add 0" clears it).
    Known meanings (from the game's source):
      game variables  0-5 vending machine selections, 6 the blackrock gem's facet, 100-108
                      the colour floor puzzle, 243 (0xF3) set when Lord Umbria dies.
      quest bytes     128 lines of power cut, 129 pit fights won, 130 key gems used,
                      133 Jospur's debt, 134 the Killorn countdown (12.6), 135 bloodworms
                      killed on level 4, 141 worlds visited, 143 cutscene + 1.
      X clocks        0 time of day, 1 the castle plot, 2 key gems treated, 3 the djinn,
                      14 best pit record, 15 "something changed" (10.5).
    Who uses them:
      set variable trap    numbers 0-415 (9.17); fine y bumps X clock 15;
      check variable trap  numbers 0-415 (9.18);
      schedules            event 9 sets, event 10 tests, event 4 sets a quest flag, event 7
                           hack 1 sets (10.5);
      conversations        GetTrapVariable / SetTrapVariable with the same numbers (so a
                           conversation can also set an X clock: SetTrapVariable(401, 16)
                           sets the castle clock to 16); GetQuest / SetQuest (flags 0-127,
                           bytes 128-143); and in the shipped conversations x_clock.
    The conversation's own saved variables (BGLOBALS.DAT, 6.6) are separate: traps can't
    see them.
    Don't reuse a byte the game uses for something else: quest 134 is also the brain
    creatures' kill counter in Killorn Keep, and Prison Tower goblin conversations set it,
    which makes the first brain creature kill start the countdown (12.6).

10.2) Conversations
  No conversation built-in sets off a trap directly. A conversation acts on traps through
  what they share:
    - variables: set one that a check variable trap tests, or read one a trap has set
      (GetTrapVariable / SetTrapVariable, GetQuest / SetQuest; 10.1);
    - doors: HandleDoor (built-in gronk_door) opens, closes or toggles the door on a square.
      The door's own open trigger (UW2 also close) fires, as nobody: in UW2 that trigger
      needs bit 9; in UW1 it fires as for an object;
    - objects: GetItem... / SetItem... (built-in x_obj_stuff) read and write any object's
      quality, owner, heading, flags, link ("special"), and with GetItemArg2/3 and
      SetItemArg2/3 its id bits 9 and 10. On a trigger that means its target square
      (quality, owner), its trap (link), "keeps its trap" (bit 10, Arg3) and in UW2 "objects
      and nobody" (bit 9, Arg2): a conversation can re-arm, disarm or retarget a trigger, or
      fix a trap's count (flags; the game writes all 4 bits). UW1 sets the 512 bit of any
      link it writes, so it can link a trigger only to an object numbered 512-1023
      (inferred);
    - UW2 schedules: when a conversation ends, the game brings every schedule up to date
      (10.5) and then runs 8 timer ticks. So a conversation that changes an X clock, or a
      variable a block 15 test reads (and bumps X clock 15), makes the matching schedule
      rows run as soon as it closes, and they can fire scheduled triggers (event 5). This
      is how the shipped game turns a conversation into a trap chain (12.1).
  Other built-ins that touch the world: CreateItem (do_inv_create) makes an item in the
  NPC's inventory and TakeItemByID / TakeItemByPos (take_from_npc...) move it to the player
  (12.8); RemoveItem (do_inv_delete); PlaceItem (place_object); SetRaceAttitude,
  SetNPCAttitude, SetAttitude; RemoveNPC (remove_talker).
  UW2 conversations also have x_clock (read or set an X clock; setting clock 0 also moves
  the game time, 20 minutes a step), teleport_player and teleport_talker (made when the
  conversation closes, with the teleport trap's rules), babl_hack (the Pits of Carnage
  fights, Jospur's debt, recharging a wand and other special cases), x_exp, x_obj_pos and
  more. The editor's conversation language (chapter 6) does not offer these; use
  SetTrapVariable(400 + n, value) to set X clock n instead of x_clock.

10.3) Plot code
  Some events are hard-coded in the games' code and only read or fire traps.

  UW1
    Special deaths [event/WORLDEV.C death_check]:
      whoami 0x1B (Garamon)   dying clears the "talismans may be destroyed" flag.
      0xE7 (Tyball)           cutscene 2; dreams bit 2 set; the first active critter of 9
                              of his 10 ally kinds is removed (a loop slip skips whoami
                              0xDE); every move trigger on square (23, 56) is
                              freed (12.14). Their traps stay, with their counts unchanged.
      0x16                    never dies: surrenders once (500 experience) and talks.
      0x0B                    talks and is left with 60 hit points.
      0x6E, 0x8E, 0x18        set quest bits 4, 11 and 6.
    Garamon's grave [obj/USEITEMS.C UseBonesOn]: using bones with owner 0x3E on a gravestone
    (0x165) whose link is the special value 0x221 sets the talisman flag, changes the
    grave's link to 0x222, runs conversation 0x1B, and fires the first object on square
    (54, 52) of the CURRENT level as a move trigger set off by the player. Shipped: the
    grave is on level 5 at (54, 54); the trigger at (54, 52) creates Garamon's ghost
    (12.7).
    The talismans [motion/OBJPHYS.C mob_to_static]: an object whose COMOBJ fate is 10 coming
    to rest on lava on level 8 near (32, 32) is destroyed and counted (12.7).
    Tyball's orb: using the orb rock on the orb (0x117) destroys it; no trigger involved.
  UW2
    Special deaths [event/WORLDEV.C death_check], among them:
      castle people (0x81-0x8F, Syria 0xA8, guard 0x95)  can't be killed: they drop to a
                     third of their hit points and the guards are called out through the
                     scheduled triggers on (15, 29) (8.9); Lady Tory (0x8D) can die once
                     the castle clock reaches 8.
      0x3A (the brain creatures)  count to 2 in quest 134, then start Killorn's
                     countdown (12.6).
      0x2F (Mors Gotha)  in Killorn Keep she talks instead of dying (or vanishes after the
                     crash); elsewhere she talks, quest 64 is set, then she dies.
      0x8C (Patterson)  the castle clock becomes 13 (14 if the djinn is caught), never
                     lower.
      0x91 (the Listener)  dies only to Altara's dagger (which breaks): castle clock + 1.
      0x98 (Bliy Skup Ductosnore)  fires the triggers at (58, 18) and (60, 18).
      0x20 (Praecor Loth)  his liches die, quest 7 is set (create object traps in world 6
                     stop working), and the trigger at (1, 2) fires.
      0x48 Mokpo, 0x2C Mystell, 0x65 Blog: quest flags and X clock 15 + 1.
      Many others set quest flags.
    fire_trigger_at callers: see 8.10.
    Level rules [game/GAMEWRAP.C do_level_hacks]: arriving on level 1 opens the door at the
    arrival square; leaving the Prison Tower checks the alarm, and leaving its level 2
    fires the triggers at (31, 36) and (35, 34); leaving Killorn level 1 (level 17) while
    the keep is about to crash makes it crash at once (12.6); arriving in the Tomb after
    Loth's death kills his undead; the Ethereal Void switches the automap off.
    The blackrock gem (hacks 54 and 55), the castle household's round (hack 36) and the
    courtyard (hack 34) are code run by hack traps (9.7).

10.4) Time
  UW1
    UW1 has no timer triggers and no schedules: nothing happens by the clock except
    - wandering monsters: every 24 slow updates (8 minutes of game time), chance 1 in 4,
      every spawner at least 8 squares from the player runs (9.11);
    - sleep: every open door closes with chance 3 in 10 (unless its tile has door bit 1),
      without firing any trigger; and if the sleep is not interrupted, every spawner runs,
      wherever it is.
    For anything repeating, the player must set it off: repeatable move triggers (a row of
    them for a corridor), levers, buttons.
  UW2
    - Timer triggers fire every (z + 1) / 4 s near the player (8.8).
    - X clock 0 (the time of day) steps every 20 minutes, and block 0 of the schedules runs
      then (10.5). Sleep and jail pass time and run all schedules.
    - Wandering monsters: every 30 slow updates (10 minutes), chance 1 in 4, spawners 8 or
      more squares away; at a sleep that is not interrupted, all.
    - Doors close by themselves with chance 3 in 10 when the player goes to sleep, and by
      schedule hack 4; their
      close triggers fire as nobody.
    - Killorn's countdown runs on the 20-second slow update (12.6).

10.5) UW2 schedules (SCD.ARK)
  The schedules move NPCs and change the world as the plot advances. They are the only
  way to make something happen on a level the player is NOT on: each level catches up when
  the player arrives. Edit them with Tools > Schedules.

  Blocks and clocks
    - SCD.ARK has 16 blocks. Block n follows X clock n: block 0 the time of day (72 steps of
      20 minutes, wrapping at midnight), block 1 the castle plot, block 2 key gems, block 3
      the djinn, block 14 the pit record, block 15 the "changed" counter. The shipped file
      has rows only in blocks 0, 1, 14 and 15.
    - Each block also keeps a clock for each of the 80 levels: how far that level has got
      in the block, and which row it reached.
    - A new game copies DATA\SCD.ARK into the game in progress; a saved game has its own
      copy. Tools > Schedules edits the open save's copy, or DATA's.

  Rows
    Each row is 16 bytes: time (a value of the block's clock), level, once, event and 11
    parameter bytes (bytes 5-15; "word at 5" means bytes 5 and 6, low byte first).
    - Level: the level number (1-80), 255 any level, 246 + n every level of world n.
    - Once: the row deletes itself after running.
    - Event: the code below; negative means disabled (run only by a test row, below).
    - Keep the rows of a block sorted by time.

  When they run
    All 16 blocks are brought up to date, for the level the player is on, at: the end of
    every conversation; entering a level or restoring a game; sleep and jail (time passes);
    hack trap 37; Killorn's crash. Separately, every 20 minutes block 0 alone is updated.
    Bringing a block up to date:
    1. The level's clock in that block is set to the block's X clock (block 0: the time of
       day).
    2. If the clock did not change, nothing runs.
    3. If it went forward, the rows from where the level had got to, with times up to the
       new clock, are offered in order. Block 0 that wrapped past midnight first runs to
       the end of the day, then from 0.
    4. If the clock went BACK, the level starts again from row 0, so every row up to the new
       time runs again, including rows without "once".
    5. Block 15 always starts again from row 0 (so every due row in it is offered each time
       X clock 15 changes; the shipped rows there are all time 0 and guarded by tests).
    6. A row runs only if its level matches the player's level and its event is not
       negative.

  Row events (byte 4)
    1   change goal: critters (word at 5) get goal byte 7, goal target byte 8.
    2   teleport: critters (word at 7) move to square (byte 5, byte 6) ON THE CURRENT LEVEL,
        only if the player can see neither the critter nor the destination (within 8
        squares and roughly in front of him; walls are ignored), unless byte 10 is set.
        Byte 11 set makes the destination its home. If it could not move and byte 12 is
        above 0, a one-off copy of the row is added to block 0 at the time of day + byte 12
        to try again. Byte 9 is not used.
    3   kill: critters (word at 5) die. Byte 7 0 spares the NPC being talked to.
    4   quest flag byte 5 = byte 6 (use 0 or 1).
    5   fire every scheduled trigger on square (byte 5, byte 6) (8.9).
    7   special case by byte 5:
          1  for critters (word at 6) standing on (byte 8, byte 9): set variable (word at 10)
             by operation byte 12 with value (word at 13);
          2  critters (word at 8) move to a random free square of (byte 10, byte 11) -
             (byte 12, byte 13), which becomes their home (only those on (byte 6, byte 7)
             unless that is (0, 0));
          3  every tile whose floor is byte 6 gets, one time in two, floor byte 7 and its
             height raised by the word at 8 (12.5);
          4  doors close (byte 6 not 0: only doors 8 or more squares from the player; 0:
             all, then 8 timer ticks);
          6  critters (word at 6) turn to face heading byte 8;
          7  critters (word at 6) move into the rectangle (byte 8, byte 9) - (byte 10, byte
             11): the first free square of each row, so they end in the last row with
             room; their home is set wrongly (12.1).
          0, 5  nothing.
    8   attitude byte 7 for critters (word at 5).
    9   set numbered variable (word at 5) by operation byte 7 with value (word at 8).
    10  test (below).
    11  remove critters (word at 5) from the map.
    0, 6  nothing.
    12 and up: STOPS ALL SCHEDULES (below).
    "Critters (word)": low byte the mode, high byte the value: mode 0 every active critter
    with that whoami, 1 every active critter of that race (not loners), 2 the object with
    that index, 3 every active critter. "Active" means on the level the player is on.

  Tests (event 10)
    Word at 5: the first variable; byte 7: how many; byte 8: the operation combining them;
    byte 9: invert; word at 10: the value. The test passes when the result equals the value
    (differs, with invert). When it passes, each following row with a NEGATIVE event is
    enabled, run and disabled again (a once row deletes itself), until a row with a
    positive event, or after running a disabled test (-10), which starts the next block of
    conditional rows. When it fails, nothing happens. The shipped tests all compare one
    variable with a number 0-6.

  Pitfalls
    - An event code of 12 or more does not get skipped: when its level matches the player's,
      it stops the block AND every later block, every time the schedules run, for good.
    - Block 0 times must be 0-71.
    - Setting an X clock BACK reruns every row up to the new time, including the non-once
      rows. Use "once" for anything that must happen only once.
    - A set variable trap or conversation that changes an X clock does not run the schedules
      at once; they run at the next update (conversation end, level change, sleep, hack 37).
      A quest set by plot code without touching X clock 15 is noticed by block 15 only
      after something else bumps X clock 15.
    - Each level remembers where it got to in each block. In a saved game, a row added at a
      time a level has already passed will not run for that level (inferred): add rows at
      future times.
    - Rows act only on the level the player is on (event 2 can't move a critter to another
      level), and only when the player is on a level the row names.
    - Scheduled chains run as nobody (8.9).

  The Schedules window
    Tools > Schedules (UW2 only): pick a block (shown with its clock), then each row shows
    time, level, a "once" box, event, the parameters (bytes 5-15 as 11 hex bytes) and what
    the row does. "^" and "v" move a row among rows of the same time, "+" copies it, "x"
    deletes it. "Add row" adds one at the end; "Sort by time" sorts; "Save SCD.ARK" refuses
    to save a block that is out of order.

10.6) Skills and spells
  Finding and disarming
    In look mode, looking at an object rolls the Search skill to find a trap in it; if one
    is found, the game asks "You found a trap! Do you wish to try to disarm it?" and rolls
    the Traps skill. The Remove Trap spell makes both rolls at skill 45; UW2's Detect Trap
    spell only the first.
    - UW1 finds only the FIRST trap-class object in the object's contents, and only if it
      is a damage, teleport or arrow trap, or a trigger whose trap is one. Rolls: Search
      against 8, Traps against 8.
    - UW2 finds a 0x1Bx trigger anywhere in the object's contents, whatever its trap.
      Rolls: Search against 10 + 2 x world, Traps against 8 + world.
    - Success: "The ... was successfully disarmed." UW2 deletes the trap with all its
      triggers. UW1 frees the object's contents from the start of the list up to the trap,
      so anything ahead of the trap in the object is destroyed too.
    - A bad failure: "Your bumbling attempts have set off the ...": the trigger fires with
      mode -1 (or the plain trap goes off and is deleted).
    - A near miss: "Unable to defuse trap."
    - UW2 calls a damage trap with an owner a "poison trap" in these messages.
    The object's look triggers fire after the detection roll either way.
  Reveal
    The Reveal spell finds a look trigger in its target (UW1: anywhere in the contents; UW2:
    the first 0x1A3) and fires it as the player with Search 45 for the roll (8.3). UW1's
    area spell trap with Reveal (class 6, owner 1) fires look triggers in objects around it.
  Rune of Warding (UW1)
    Casting it lays, about a square in front of the player, a move trigger (invisible,
    enchanted, no bit 11, so only critters set it off, once) aimed at its own square, and a
    ward trap of quality 63 (any critter) with count 1 [event/TRIGGER.C cast_trap_spell].
    UW2 has the code but nothing calls it.
  Wards and sleeping
    While the player sleeps, a wandering monster walking up to him runs any ward trap on its
    path directly, with nobody as "who": the ward's test fails, the monster is not hurt and
    the ward stays (both games).



10.7) UW2 light: dark and lit squares
  UW1's light comes only from what the player carries (and spells). UW2 adds a minimum light per
  level, in DATA\DL.DAT (one byte per level, 80): the byte mod 10 is a light level (0 none,
  higher brighter, the levels of SHADES.DAT), and a byte of 10 or more says the minimum applies
  on squares WITHOUT the light flag, below 10 on squares WITH it [game/PLAYDATA.C load_dl]. The
  light flag is bit 8 of each square's tile word. When the player steps onto a square whose flag
  differs from the last square's, the light is redone: the minimum where it applies, otherwise
  only carried light [motion/PHYSICS.C change_GrSq]. Level 1, Lord British's castle, has 14:
  light 4 on unflagged squares; its corridors are flagged, so they are dark without a torch.
  Shipped values: Britannia 14, 13, 3, 3, 6 (the rest 0); the Prison Tower 13 (its top 3);
  Killorn Keep 13, 11; the Ice Caverns 14, 14; Talorus 12, 11; the Ethereal Void 14 or 15; the
  rest of those worlds and the Academy, the Tomb and the Pits 3 (4 for the Pits' first level),
  that is light 3 on flagged squares only. Tools > Level light edits both.

11) RECIPES: BUILDING COMMON EFFECTS
------------------------------------
  Each recipe lists what to place, the fields to set, the trigger's flags, and the
  pitfalls. Unless a recipe says otherwise it works in both games. Chapters 8 and 9 explain
  every field; the shipped example named in each recipe is a working model to open and
  copy.

11.1) The basic workflow
  1. Place the first trap on the square where it must act: right click the square, "Add
     trap", choose it. (A door trap goes inside the door instead: "Add door trap" in the
     door's panel.)
  2. Place the trigger:
     - on a tile: right click the tile, "Add move trigger" ("Trigger type": "Unlimited"
       keeps its trap, "One time only" uses it up);
     - inside an object: right click the object, "Add trigger", choose the kind (it is made
       inside the object, and its target square is set to the object's square). Levers
       made from the object list offer "Add use trigger to lever" in their create window.
  3. Link: right click the trigger, "Link trigger", and click the trap (or the door). The
     target square becomes the trap's square and the trap's trigger count is updated. For a
     lever, right click the lever and choose "Link lever". A trigger inside any other object
     is not on the map, so it has no right click menu: select it (the editor selects it when
     "Add trigger" makes it) and press "Create new link" in its panel instead.
  4. Further steps: select the trap and press "Add next trap / trigger"; the new trap is
     made inside it and selected. Repeat from the new one.
  5. Set the fields in the Basic tab; fine x/y, z and heading in the Advanced tab where the
     Basic tab has no control for them.
  6. Check: in the trigger's panel the right "can set it off" boxes and the keep box; in the
     first trap's panel "Triggers pointing here" equal to the count (chain steps: leave the
     1 the editor gives them, see 8.4); Tools > Fixes for the level.
  Remember: a trigger's chain runs at its target square; a create object, delete object or
  door trap ends the chain; a one-shot trigger deletes its chain even if nothing happened.

11.2) An ambush
  The player walks into a room and a monster appears.
  Place:
    - A create object trap (0x187) on the square where the monster should appear (open,
      ideally out of the player's view).
        "Spawn chance" 100 (quality 0).
        "Add template", choose the critter. In the template: Attitude 0 (hostile); Goal 4
        (guard: attacks what comes near) or 8 (mill about); HP; in the Advanced tab Height
        = the spawn square's floor height x 8, Tile Pos where it should stand, Quality /
        Owner = the spawn square (its home), Home (X / Y) = the spawn square. Give it a
        conversation (NPC name) if it should talk.
    - A move trigger on the square the player crosses: "One time only". Place it where
      every path crosses (fine x/y); its Height = the floor height x 8.
    - Link the trigger to the create object trap.
  Flags: "The player can set it off" on, "Creatures can set it off" off, keeps-its-trap
  off. With keeps-its-trap on, every pass makes another monster (nothing limits copies of
  a non-temporary template).
  Variants:
    - Two monsters: two move triggers on the same tile, each linked to its own create
      object trap (the chain ends after a create, so one trap can't make two). UW1 level 7
      (15, 43) does this with two dread spiders.
    - Loot: a template may hold one object (a key); only the first is copied (UW1 level 5
      (54, 2): a dire ghost carrying a key).
    - Pick-up ambush: put the trigger in the bait instead: right click the item, "Add
      trigger", "pick up trigger", then link it to the trap. The item must not be a stack
      or have a special property. For several baits, link each bait's trigger to the SAME
      trap: the first one picked up spawns the monster and deletes the trap and the other
      triggers (UW1 level 3 (40, 11): a broken axe, a broadsword and a broken mace, one
      bandit).
  Pitfalls: the spawn square must have room; if the trap's count ever drops to 0 while it
  still exists it becomes a wandering monster spawner (9.11); in UW2 world 6 nothing is
  created after Praecor Loth's death.
  Shipped: UW1 level 1 move trigger (3, 36) -> create at (3, 33), a goblin; level 5 (13, 48)
  -> (19, 50), a fire elemental; level 3 pouch at (49, 52) -> a headless at (44, 55).

11.3) A lever, switch or button that spawns an enemy
  Shipped model: UW1 level 3, switch 0x173 at (38, 44) on the west wall of an alcove (fine
  x 0, heading 6, z 112). It holds a use trigger (target (42, 42), flags 6: player,
  repeatable) linked to a create object trap at (42, 42) (quality 0, count 1), whose
  template is a giant rat (0x43): HP 7, goal 4, attitude 0, home (42, 42). Every press
  makes another rat.
  Place:
    - The create object trap and template as in 11.2.
    - A lever or switch: Objects > Add Object (or right click a tile, "Add object") and
      choose it; in its create window keep "Add use trigger to lever", choose "Unlimited"
      or "One time only", keep "Snap to nearest wall", set "Height".
    - Right click the lever, "Link lever", click the create object trap.
  Pitfalls:
    - The lever panel's "Add trigger" button makes a use trigger the player can set off
      and that keeps its trap; untick "Reusable" on it for a one-time spawn.
    - Buttons and switches 0x170-0x17F flip on every use; with one trigger it fires both
      ways. With two triggers the first fires when turned off, the second when turned on
      (8.2).
    - A wrong combination elsewhere can spawn a monster too: UW1 level 3's button puzzle
      creates a skeleton at (1, 8) from its else branch (11.9).

11.4) Arrow traps that fire when you pass, and a volley
  Place:
    - A move trigger where the player is to be shot at ("One time only" or "Unlimited").
    - An arrow trap (0x182) on an OPEN square up the corridor (the missile starts in the
      arrow trap's target square, at the trap's own fine x/y and z):
        "Projectile": the missile, e.g. a crossbow bolt (0x11) or an arrow; UW1's level 2
        uses boulders (0x154), level 4 skulls and bones;
        "Direction": towards the trigger (0 north, 2 east, 4 south, 6 west);
        "Height": about the floor height x 8 + 16;
        Tile Pos: the launch point in the square.
    - Link the trigger to the arrow trap.
  Volley: select the arrow trap, "Add next trap / trigger", choose another arrow trap, and
  give it its own projectile, direction, height and fine x/y (all launch from the same
  square). Add as many as you like; end with a text trap for a message ("You hear a
  rumbling sound to the west!" on UW1 level 2).
  Pitfalls: a launch point inside a wall makes a dud (UW1 level 8 (47, 32) fires a bolt
  straight into the wall north of it, inferred); the trap does not aim at the player, only
  along its heading; UW1 adds about 3 degrees clockwise.
  Shipped: UW1 level 5 move trigger (19, 51) -> bolt from (19, 46) heading north; level 4
  (54, 6) -> skull, bone, skull from (56, 6).

11.5) A poison trap
  Shipped model: UW1 level 3. Two move triggers at (1, 7) and (1, 9) among plants (flags
  6: player, repeatable) link to a damage trap at (1, 10), inside the rock: quality 4,
  owner 1, count 2. After it a text trap prints "You feel the sting of tiny poisonous
  needles stabbing into the exposed parts of your legs and arms."
  Place:
    - A damage trap (0x180) anywhere (it can sit in solid rock): "Damage" = strength 1-15,
      "Poisons the player ... instead of damaging" on.
    - One or more move triggers ("Unlimited" to sting every time), each linked to it; the
      count follows the number of triggers.
    - Optionally "Add next trap / trigger" on the damage trap: a text trap with the
      message.
  Pitfalls: strengths above 15 wrap (16 does nothing); a player already more poisoned, or
  resisting poison, is not affected; critters setting it off (if allowed) take plain damage.
  Poisoned item: create a potion with "Is a trap" ticked in its create window and choose a
  damage trap (quality = strength, owner 1); drinking it poisons and deletes the trap (UW1
  level 2 (14, 51), strength 10).

11.6) Continuous or repeating fireballs
  UW2: plates that fire down the corridor (the Tomb of Praecor Loth, 12.10)
    - A pressure trigger (0x1A4; the Tomb uses 0x1B4, but a trigger lying on a tile can't

      Z about two steps above the floor (the Tomb uses 96-116, mostly 112, on floors of
      height 12).
    - Link every plate to its spell trap (several plates may share one trap).
    - A second shot: "Add next trap / trigger" on the spell trap, another spell trap.
    It fires on every step onto the plate.
  UW2: a timed turret
    - A timer trigger (0x1A9) near the turret: flags 6, Height (its z) = interval in
      quarter seconds - 1 (z 10: every 2.75 s; z 7: every 2 s), target square = the spell

    - A spell trap there, as above. For a second turret elsewhere in the same chain, add a

    - It fires only while the player is within 8 squares of the target square; the editor

  UW2: fireballs that never stop

    They must be in the level's active list. Copy one from level 51 (whether the editor's
    paste keeps their speed was not checked).
  UW1 (no timers)
    - A spell trap: Quality 5, Owner 1-4 (1 magic arrow, 2 lightning bolt, 3 fireball, 4
      acid), "Direction", "Height", Tile Pos as the launch point.
    - Repeatable move triggers linked to it, on the squares the player must cross (several

    - Shipped: level 5, move trigger (14, 45) -> fireball from (10, 45), heading east, z 51.

11.7) A secret door opened by looking (or searching)
  Shipped model: UW1 level 3 (37, 9). A look trigger (z 7, one-shot) inside a special
  texture object (0x16E) painted on the wall face sets off a change terrain trap at (37,
  10): quality 23, owner 63, z 96: the solid square opens at height 12 with its textures
  unchanged. Its next step is a look trigger aimed at (36, 10), where a delete object trap
  removes the texture object from (37, 9).
  Place:
    - The decoration: Add Object, a special texture object (0x16E, "Texture" picks the wall
      picture), on the wall face of the hidden square (Tile Pos on the edge, "Direction"
      pointing at the wall, "Height"; the shipped one at (37, 9) has fine y 7, heading 0).
    - Right click it, "Add trigger", "look trigger". Its "Search difficulty (Z)": 0 is
      always noticed; otherwise the chance is (15 + Search - z) / 31.
    - A change terrain trap on the hidden square: "Extra tiles X" 0, "Extra tiles Y" 0 (in
      the create window "Size X", "Size Y"), "New tile type"
      Open, "New floor height" = the corridor's, "Use current floor texture" and "Use
      current wall texture" on (or new textures).
    - Link the look trigger to the change terrain trap.
    - To remove the decoration: select the change terrain trap, "Add next trap / trigger",
      choose a delete object trap; in its panel press "Create new link" and click the
      decoration.
  Variants: a button or lever instead of the look trigger (a use trigger), or a "pull
  chain". The vines on UW1 level 3 (52, 12) are moved aside by a look trigger the same way,
  with the message "You move the vines aside..." (12.12).
  Pitfalls: with "One time only" the trigger is gone after the first success, which is
  what you want; with z above 0 a failed Search roll can be retried by looking again.

11.8) A lever that raises stairs or changes the terrain
  Shipped models: UW1 level 4, levers at (57, 31), (60, 30) and (61, 33) aim change terrain
  traps whose heading is 7 and quality odd (the tile type is kept), raising squares to
  heights 5, 7 and 9: stairs. A lever at (58, 34) opens a 2 x 4 area at height 8.
  Place:
    - A lever with a use trigger ("One time only" for permanent stairs).
    - A change terrain trap on the first square: "Extra tiles X/Y" for the area that takes ONE

    - Each further height needs its own change terrain trap on its own square. Either give

  Eight-position levers (hack 3), UW1 level 1: four levers 0x161 at (56..59, 45) hold use

    - Add Object, a dial lever (0x161): "Add use trigger to lever", "Unlimited", "Start
      position".
    - A do trap ("Special trap" 3) on the square whose height changes, Height (z) = the

11.9) A combination puzzle with set and check variable
  Shipped models: UW1 level 3, three buttons at (5, 7) change game variable 16 (one xors it
  with 3, one sets it to 56, one shifts it left by 1); the door at (6, 8) toggles when the
  xor button leaves the variable at 51 (set, shift, xor: 56, 48, 51), and a wrong state
  creates a skeleton at (1, 8) through the else branch. UW1
  level 5, the Ring of Humility (12.11).
  Design (UW1 values; one unused game variable, say 40):
    - "Digit" levers: each holds a use trigger ("Unlimited") linked to a set variable trap
      (it can lie on any square, for example the lever's): "Variable index" 40,
      "Operation type" Shift left, "Value" 2; then "Add next trap / trigger" on it: a set
      variable trap, variable 40, Or, value = this lever's digit (0-3).
    - The "check" lever: a use trigger ("Unlimited": it must survive wrong tries) linked to
      a check variable trap: "First variable (Z)" 40, "Variables after it" 0, "Pack 3 bits of each
      instead of adding" OFF (to compare the whole value), "Value checked for" = the
      answer.
        then: "Add next trap / trigger": what happens when it is right (a door trap, a
        create object trap; or first a set variable trap "solved", then the reward).
        Every step runs at the check trap's square, so place the check variable trap on
        the door's square for a door trap here, or make this step a trigger aimed at
        another square;
        else: "Add next trap / trigger" again: in UW1 this must be a TRIGGER, aimed at a
        square where you placed the penalty (a create object trap) or a reset (set
        variable 40 to 0).
    - Optional: move triggers on the floor that spoil the combination (set it to 63), as
      the Ring of Humility does.
  Pitfalls:
    - UW1 results are kept to 0-63, so a shift left drops the old high digits: with digits
      of 2 bits, the last three presses count.
    - Game variable 0 can't be set by a set variable trap. Choose a variable no other puzzle
      and no conversation uses.
    - A one-shot check trigger is deleted after the FIRST try, right or wrong.
    - UW2: the value encodings differ (9.17, 9.18): set variable value = quality x 64 +
      owner; check variable compares one variable by its low 3 bits unless fine x bit 2 is
      set; game variables are bytes.

11.10) A door only a lever can open
  Place:
    - The door, with a lock no key fits: "Add lock", then in the lock "Opened by key" off,

11.15) UW2: a one-time change keyed to a quest (the gem chamber pattern, 12.2)

     player will be, linked to:
       check variable A = 1 (Fine X 4: whole value) -> set variable B, add 1 -> check
       variable B = N (Fine X 4) -> the collapse.
     Before A is set the first check fails and the chain ends. (A check variable value v is
     written quality = v / 256, owner = (v / 8) % 32, fine y = v % 8; "add 1" is heading
     0, quality 0, owner 1. Pick game variables the game does not use, 10.1.)
  3. The collapse: change terrain traps that make rooms solid (type 0) or drop floors, a
     special effects trap (quality 4) to shake the screen, a spell trap class 11, owner 9
     (tremor), a damage trap (the timer acts as the player, so it hurts the player
     wherever he stands in range). Reach squares beyond the first through trigger steps.
  4. The lasting result on other levels: the 11.15 pattern (a quest set at the end of the
     chain with Fine Y 1, a block 15 test, scheduled triggers).
  Limits: the timer counts only while the player is within 8 squares of its target square
  (use several timers, or accept that the countdown pauses); timers fire only on the
  current level.

11.18) Giving an item from a conversation (the blackrock serpent pattern, 12.8)
  Use a conversation, not a trap. In the chapter 6 language, with a saved variable "given":
    if (given == 0)
      local castle = GetTrapVariable(401)
      if (castle > 12)
        local pos = CreateItem(277)
        local res = TakeItemByPos(pos)
        given = 1
      endif
    endif
  CreateItem makes the item (here 277 = 0x115, UW2's serpent statue) in the NPC's
  inventory; TakeItemByPos moves it to the player (2 means he could not carry it).
  TakeItemByID(277) works too. Gate it on whatever the plot needs: GetQuest, the castle
  clock (number 401), a saved variable. To make the item appear in the world instead, use a
  create object trap on a scheduled trigger (11.16) or PlaceItem.

12.7) Throwing the talismans (UW1)
  No trap or level object counts the talismans: it is all code.
  - The counter is a byte of the player's record, set to 8 at character creation;
    conversations read it through GetQuest with a number above 35.
  - A talisman is any object whose COMOBJ fate is 10 (the Object Editor's "Is talisman"):
    0x0A the shiny sword (Justice), 0x36 the iron ring (Humility), 0x37 the shiny shield
    (Valor), 0x93 / 0x97 the taper / lit taper (Sacrifice), 0xAE the shiny cup (Wonder), 0xBF
    the bottle of wine (Compassion), 0x11F the standard (Honor), 0x136 the book (Honesty).
    The test is the item id only: any object of those ids counts (inferred).
  - When a thrown or falling object comes to rest [motion/OBJPHYS.C mob_to_static], the game
    checks: it lies on lava; its fate is 10; the player is on level 8; |x - 32| + |y - 32|
    < 6; the player is alive. Then:
      if Garamon has been laid to rest (the "talisman" flag): the object is destroyed in
      fireballs and the counter goes down. At 0: "A rending sound fills the air.", a moongate
      appears at (32, 32), "The Slasher of Veils is dragged from this world.", the player is
      sent to level 9 at (27, 23), and from then on he can't die;
      if not: a bit of the player's dreams is set, and the object stays in the lava
      (inferred).
  - The pit on level 8: lava of height 1 at x 30-34, y 31-34, inside a ring of height 2 at x
    29-35, y 30-35. The Slasher of Veils (#129, 0x7C, whoami 248) stands at (32, 33), on a
    move trigger (#558, critters only, once) whose chain deletes a spell effect (0x1C7) there.
  - Enabling it: Garamon. Using bones whose owner is 0x3E on a gravestone whose link is the
    special value 0x221 sets the flag, changes the grave's link to 0x222, runs conversation
    0x1B and fires the first object at (54, 52) of the current level as a move trigger
    [obj/USEITEMS.C UseBonesOn]. Shipped: the grave #599 is on level 5 at (54, 54); at
    (54, 52), a SOLID square nothing can walk into, lies move trigger #495 (one-shot) ->
    create object #500 at (54, 53) -> template #196, a ghost (0x61), friendly, goal 7,
    whoami 27 (Garamon), home (54, 53). If Garamon (whoami 0x1B) dies, the flag is cleared.
  - The pit's place and level, the grave square and the bones' owner are constants in the

    trigger #549 -> #550: opens (46, 7).
  This is the pattern for acting on several squares from one lever: each change after the
  first is reached through a trigger used as a chain step, whose target square is where the
  next trap lies.

12.13) The eight-position levers (UW1, level 1)
  - Four levers 0x161 (#623, #870, #871, #872) at (56..59, 45) hold use triggers aimed at
    hack traps 3 (z 16) at (49, 44), (47, 44), (45, 44) and (43, 44).
  - Each use steps the lever's position (0-7) and then sets the matching square's height to
    (16 + 8 x position) / 8 = position + 2. A walkthrough explains that the levers stand for
    the heights of the pillars.

12.14) Tyball's room (UW1, level 7)
  - Move trigger #775 (one-shot) at (23, 56) -> target (24, 57): text 384 "You hear the
    portcullis slam shut behind you!" -> set variable #650 (game variable 50 = 1) -> hack
    trap 0x32 #837: the first active critter with whoami 0xD8, a feral troll guard (#251,
    goal 7, attitude 1, at (26, 56)), talks to the player at once, and then goes home.
  - A second move trigger on the same square, #888, closes the portcullis at (24, 56)
    through door trap #889 (quality 2), which gives the portcullis a copy of lock #819.
  - Tyball's death [event/WORLDEV.C TyballDeath]: cutscene 2; the first active critter of
    9 of his 10 ally kinds is removed (whoami 0xDE is skipped by a loop slip); and every move
    trigger on (23, 56) is freed, so after his
    death the portcullis no longer slams shut. Those triggers' traps are not deleted and
    their counts are not lowered.
  - UW1 has no sleeping critters; a guard "waiting" with goal 7 woken by hack 0x32 is the
    nearest thing.


13) LIMITATIONS
---------------

13.1) Hard-coded in the games
  These are constants and special cases in the games' code. No change to the levels, the
  schedules or the conversations can move or remove them; a mod has to work with them (or
  patch the executable, which this editor does not do).
  UW1
    - The talismans: destroyed only on lava on level 8 within |x - 32| + |y - 32| < 6; the
      moongate appears at (32, 32) and the player is sent to level 9 at (27, 23). What counts
      as a talisman (COMOBJ fate 10) can be changed in the Object Editor; the place can't.
    - Garamon: the grave must have the link value 0x221 and the bones owner 0x3E; using them
      fires the first object on square (54, 52) of the current level and runs conversation
      0x1B; whoami 0x1B's death clears the talisman flag.
    - Tyball (whoami 0xE7): his death plays cutscene 2, removes one critter of each of his
      allies' kinds (a fixed list of whoami, one skipped) and frees every move trigger on
      square (23, 56).
    - Special deaths for whoami 0x16, 0x0B, 0x6E, 0x8E and 0x18 (10.3).
    - Level 7: arriving without having destroyed Tyball's orb sets the player's maximum mana
      to 0 (given back, at a quarter, when he leaves); the orb (0x117) and the orb rock undo
      it. The mages of that level behave differently until then.
    - Level 9, the Ethereal Void: the player slowly loses hit points, the screen flashes and
      shakes, there is no compass, the inventory shows a message, the level is fully lit, no
      exploration experience is given, and no spell cast by the player or a critter works
      (a trap's spell of class 0-11 is tested only for anti-magic).
    - Exactly 9 levels.
    - The hack traps' cases and their fixed places: the bullfrog puzzle only on level 4 at
      (48, 48); the talking door is conversation 0x19; hack 0x32 calls whoami 0xD8.
  UW2
    - Killorn Keep's crash: the counter, the countdown and the crash are tied to whoami 0x3A,
      to quest byte 134 and quests 50 and 54, and to leaving level 17. Reusing whoami 0x3A on
      a world 2 level is the only way to get it elsewhere without code.
    - Mors Gotha (whoami 0x2F) can't die in world 2.
    - The castle people (whoami 0x81-0x8F, Syria 0xA8, guard 0x95) can't be killed; the guards
      come from the scheduled triggers on (15, 29).
    - The squares fire_trigger_at uses: (58, 18) and (60, 18) for Bliy Skup Ductosnore's
      death, (1, 2) for Praecor Loth's, (58, 5) for hack 25, (39, 37) for jail, (31, 36) and
      (35, 34) when leaving level 10.
    - World rules: no creation in world 6 after quest 7; Loth's undead die on arrival there;
      the Ethereal Void turns the automap off and refuses teleports out of world 8 while the
      player dreams; the jail cell and quests 112/124; the Pits of Carnage arena; leaving the
      Prison Tower checks the alarm; leaving Killorn level 3 or Academy level 3 takes the
      telekinesis wand away.
    - The blackrock gem: its square on level 5, its facets by castle clock (X clock 1), and
      hacks 54/55. Hack 32's fixed object numbers, hacks 25, 30, 31, 34 and 36.
    - What the X clocks, quest bytes and the schedule event codes mean to the code (10.1,
      10.5).
  Both
    - What an item id IS (a door, a lever, a potion, a key) is fixed by the code; the
      Object Editor changes the numbers in OBJECTS.DAT and COMOBJ.DAT (weight, damage,
      toughness, fate...) but not the kind. The trigger kinds and trap types are fixed too.
    - Death, sleep, the clock rates and the AI goals are code.

13.2) Limits of the data
  - A level holds at most 1024 object records: 256 mobile (critters, missiles; 0 is "none"
    and 1 the player) and 768 static. Each create object trap's template uses a mobile or
    static slot too.
  - A trap's trigger count is 4 bits: at most 15 triggers per trap.
  - UW2: at most 64 timer triggers per level (8.8).
  - Game variables: UW1 64 of 0-63; UW2 256 of 0-255 (bytes). Quest bits: UW1 32, UW2 128.
  - A trap's quality and owner are 6 bits (0-63), z 7 bits, heading and fine x/y 3 bits:
    every formula in chapter 9 is limited by them (a change terrain covers at most 8 x 8
    squares; an arrow trap's missile id needs owner below 32; a UW1 set variable stores 6
    bits).
  - UW1 has no timers and no schedules: only the player's actions, the critters' movements,
    sleep and the wandering monster clock set traps off.

13.3) Where the editor differs from the shipped levels
  Linking a trigger
    In every shipped level a trigger has Is quantity set, its link is its trap's index, and
    the trap lies in the object list of the trigger's target square (8.1). The editor's
    "Link trigger" (right click), "Link lever" and "Create new link" make exactly that. But
    "Add next trap / trigger" in a trigger's panel (and so any chain started that way)
    creates the trap INSIDE the trigger and clears the trigger's Is quantity. The game still
    runs it (it follows the link either way), but other code treats the trap chain as the
    trigger's contents. What that means (inferred from the code, not tested in the game):
    - A one-shot trigger made that way: when it is used up, the game removes the trigger,
      then looks for its trap in the target square's list, does not find it, and leaves the
      trap and its whole chain in memory, unreachable. Nothing visible happens, but those
      object slots are lost for the rest of the game.
    - A trigger made that way inside an item the player can carry (a pick-up, use or look
      trigger): the chain goes into the inventory with the item, and the game copies it with
      the player's inventory from level to level.
    - The editor's "Triggers pointing here" still counts it, so the count is right.
    So link triggers to traps with "Link trigger", and use "Add next trap / trigger" for the
    steps after the first trap, where the shipped levels also store the next step inside the
    previous one. Tools > Object fields shows a trigger's Is quantity.
  Other differences
    - Templates and locks must be INSIDE their create object or door trap (made with "Add
      template", "Add lock"); "Create new link" on those traps would set Is quantity and the
      game would ignore the template or lock.
    - Delete object traps and the UW2 hacks that act on an object hold a reference (Is
      quantity set); "Link trap" and "Create new link" make that.
    - New UW1 chain traps get fine x/y 3, 3 and new UW2 traps 0, 0; several traps read
      these fields (chapter 9), so check them.
    - UW2: the editor writes the timer list itself (8.8). The shipped levels list every
      timer trigger, which is what the editor does.

13.4) Bugs in the games to work around
  - UW1 kill_triggers: when a used-up trigger's trap is deleted, the game walks every
    object list looking for the other triggers of that trap, but in each list it stops at
    the first trigger it removes [event/TRIGGER.C kill_triggers: the removal clears the
    link to the next object before the walk reads it]. A second one-shot trigger for the
    same trap later in the same list (the same tile, or the same container), and anything
    after it in that list, is not examined: such triggers survive, linking to the freed
    trap, and then the count never reaches 0 so the game scans all 4096 squares. A
    surviving trigger later runs whatever object reuses that slot as if it were a trap
    (inferred). Keep at most one one-shot trigger per trap in any one list. (UW2 fixed it.)
  - UW1 0x1A4 "step on" triggers never fire (8.5).
  - UW1 look triggers in carried objects may not fire, because the inventory look sends the
    event before it knows the object (8.5).
  - UW1 disarming frees everything ahead of the trap in the object (10.6).
  - UW2 enter and exit triggers fire only as the first trigger of their tile (8.7).
  - UW2 text traps with owner bit 5 never print (9.20).
  - UW2 single-variable check variable traps compare only the low 3 bits unless fine x bit 2
    is set (9.18).
  - UW2 schedules: an event code of 12 or more halts all schedules; event 7 hack 7 sets the
    moved critter's home to the wrong square (10.5).
  - A nested chain clears "who" for the rest of the outer chain (9.1).
  - Wards on a sleeping player's path never hurt the monster (10.6).

13.5) The old limitations list, revisited
  - Starting position: now changeable with Tools > New game start square (it is in the
    executable, not the levels). A saved game keeps the player's position in PLAYER.DAT
    (Tools > Character in a save).
  - UW2: supported (levels, schedules, conversations, saved games).
  - Level 7 and level 9 rules (UW1): still hard-coded (13.1).
  - Conversations that check hit points: possible now; GetProperty reads "npc_hp" and
    "play_hp" (6.10).
  - More than 9 levels (UW1): still impossible. UW2 has room for 8 levels in each of its 9
    worlds, not all used; an empty slot can be made into a level (2.2).
  - Changing an object's type: still impossible in the game; what you can change is listed
    in 13.1.
  - "A maximum of 460 objects": the item ids are fixed (0x000-0x1FF, of which the games
    define about 460 kinds); each level holds up to 1024 object records (13.2).
